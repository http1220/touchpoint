## 1. 인덱스 — 아웃박스 폴링 쿼리

```sql
SELECT id FROM dispatch_outbox
 WHERE status = 'pending' AND next_retry_at <= NOW(3)
 ORDER BY id LIMIT 100          -- 실제로는 FOR UPDATE SKIP LOCKED
```

### 1-1. `EXPLAIN` — 데이터 분포가 답을 바꾼다 ✅ 실측

**기대와 다른 결과가 나왔고, 그게 이 실험의 수확이다.**

| 분포 | 옵티마이저 선택 | `rows` | `Extra` |
|---|---|---|---|
| pending 2000 / sent 0 (**큐가 밀린 상태**) | **PRIMARY** | 100 | `Using where` |
| pending 20 / sent 2000 (**정상 운영**) | **`ix_poll`** | 20 | `Using where; Using index; Using filesort` |

- **큐가 밀렸을 때**는 거의 모든 행이 조건을 만족한다. `ORDER BY id LIMIT 100` 이면 **PK 를 순서대로 걸어가다 100건에서 멈추는 것**이 가장 싸다. 보조 인덱스를 타면 1924건을 훑고 filesort 까지 해야 한다
- **정상 운영 상태**에서는 pending 이 소수라 `ix_poll` 이 20건만 보고 끝난다. `Using index` 는 커버링 인덱스라 테이블을 안 읽었다는 뜻이다

> **그래서 "인덱스를 걸었더니 빨라졌다" 는 문장은 쓸 수 없다.**
> `ix_poll` 이 값을 하는 것은 **pending 이 전체의 소수일 때**, 즉 워커가 큐를 따라잡고 있을 때다. 밀려 있을 때는 옵티마이저가 인덱스를 버리는데, **그건 옵티마이저가 맞는 판단을 한 것**이다.
>
> 인덱스 실습에서 흔히 하는 실수가 여기 있다 — 빈 테이블이나 전부 조건을 만족하는 테이블로 재면 인덱스가 안 먹는 것처럼 보인다. **분포를 만들어야 측정이 성립한다.**

### 1-2. `Using filesort` 는 왜 남아 있는가 ✅ 실측

`ix_poll` 을 타도 filesort 가 붙는다. 컬럼 순서가 `(status, next_retry_at, id)` 인데

- `status` 등호 → 인덱스 앞부분 고정
- `next_retry_at` **범위** → 여기서 정렬 순서가 깨진다
- 그 뒤 `id` 는 **정렬에 쓸 수 없다**

범위 조건 뒤의 컬럼은 인덱스 순서로 정렬에 쓰지 못한다. `id` 를 마지막에 둔 것은 정렬 때문이 아니라 **커버링**을 위해서다 — 실제로 `Using index` 가 나왔고 테이블 접근이 없다.

정상 운영에서 filesort 대상은 20건이라 무시할 만하다. 밀렸을 때는 옵티마이저가 PK 경로로 가버리므로 어차피 filesort 가 없다.

### 1-3. 새 인덱스가 기존 쿼리를 흔들었다 ✅ 실측

좀비 회수용으로 `ix_zombie (status, claimed_at)` 를 추가한 직후, 폴링 쿼리의 계획이 바뀌었다.

```
type: ref   key: ix_zombie   rows: 2002   Extra: Using index condition; Using where; Using filesort
```

둘 다 `status` 로 시작해서 옵티마이저가 더 좁은(2컬럼) 쪽을 골랐는데, 그쪽은 `next_retry_at` 을 걸러 주지 못해 2002건을 훑는다. 분포를 정상 운영으로 바꾸자 다시 `ix_poll` 로 돌아왔다.

> **인덱스를 추가하는 일은 기존 쿼리의 계획을 바꾸는 일이다.** 추가할 때 그 인덱스를 쓸 쿼리만 보면 안 되고, **같은 선두 컬럼을 가진 기존 인덱스가 있는지** 봐야 한다.

## 2. 워커 동시성 — `SKIP LOCKED` ✅ 실측

2000건을 적재하고 워커 4개(`--scale worker=4`)로 비웠다. 네트워크를 변수에서 빼려고 `NoopChannel` 로 측정했다.

| 항목 | 값 |
|---|---|
| 아웃박스 적재 | 2000건 |
| 워커 | 4개 (`WORKER_BATCH_SIZE=100`) |
| 소요 | **10.6초** (약 189건/초) |
| `dispatch_log` 행 | 2000 |
| `DISTINCT outbox_id` | **2000** |
| **`(outbox_id, attempt)` 중복 쌍** | **0** |

```sql
SELECT COUNT(*) FROM (
  SELECT outbox_id, attempt FROM dispatch_log
   GROUP BY outbox_id, attempt HAVING COUNT(*) > 1
) t;
-- 0
```

**워커 넷이 같은 행을 집지 않았다.** 선점과 상태 변경을 한 트랜잭션에 넣고 `FOR UPDATE SKIP LOCKED` 로 잠근 결과다 → [ADR-004](decisions/ADR-004-skip-locked.md)

> 적재가 2000건에 **12.4초**로 전송(10.6초)보다 느렸다. 전환 하나마다 트랜잭션을 열기 때문이다. 실제 서비스에서는 전환이 사용자 행동에 맞춰 흩어지므로 문제가 아니지만, **시드 자체는 배치 삽입으로 바꿀 여지가 있다.**

## 3. 구간별 소요 시간 ✅ 실측

Noop 채널 500건. 네트워크를 빼면 **무엇이 남는지** 보려는 측정이다.

| 구간 | 평균 | 최소 | 최대 |
|---|---|---|---|
| `total_ms` | **4.9** | 3 | 10 |
| `db_ms` (선점 배분 + 결과 반영) | **4.8** | | |
| `parse_ms` | 0.0 | | |
| `send_ms` | 0.0 | | 네트워크 없음 |

**`db_ms` 가 `total_ms` 의 거의 전부다.** 전송을 빼면 남는 비용은 DB 뿐이라는 뜻이고, 이건 예상대로다. 의미는 **GA4 를 붙였을 때 `send_ms` 가 190ms 라면 전체의 97%가 네트워크**라는 것 — 최적화할 곳은 우리 쪽이 아니라 배치 크기와 동시성이다.

> ### 첫 측정이 틀렸던 이야기
>
> 처음에는 `db_ms` 평균이 **31.6**, `total_ms` 평균이 **7.8** 이었다. 구간의 합이 전체보다 큰 값이다.
>
> 배치 전체의 선점 시간을 **모든 행에 그대로** 더하고 있었다. 100건을 한 번에 집었으면 그 시간이 100번 더해진다.
>
> 구간을 나눠 적는 이유가 *"합이 맞아야 어디가 느린지 안다"* 인데, 합이 안 맞으면 아무 말도 못 한다. 건수로 나눠 배분하도록 고치고 다시 쟀다.
>
> **계측 코드도 검증 대상이다. 숫자가 나왔다고 맞는 숫자가 아니다.**

### 3-1. 채널별 비교

| 채널 | `send_ms` | 표본 | 비고 |
|---|---|---|---|
| Noop | 0.0 | 500 | 네트워크 없음 |
| GA4 (검증 엔드포인트) | 185 · 186 · 193 · 196 | 4 | eu-north-1 → `www.google-analytics.com` |

GA4 표본이 4건뿐이라 평균이라 부르기 이르다. 다만 편차가 좁고(185~196ms) **네트워크가 지배적**이라는 결론에는 충분하다.

## 4. 재시도 백오프 — 값을 실험으로 정한다

### 4-0. 지터가 실제로 흩어지는가 ✅ 실측

타임아웃을 1ms 로 낮춰 두 건을 동시에 실패시켰다. 둘 다 `attempt=1` 이고 기본 대기는 30초다.

```
id 9  → next_retry_at 12:09:33.894
id 10 → next_retry_at 12:09:35.908     같은 배치, 2.0초 차이
```

> 매체가 잠시 죽었다 살아나면 실패한 전송이 **전부 같은 시각에** 재시도된다. 막 회복한 매체를 다시 넘어뜨리는 것이 그 지점이다. 지터 ±20% 가 흩뿌리는 것을 두 건으로 확인했다 — 표본이 작으니 건수를 늘려 분포로 다시 잰다.


**초기 후보**

| attempt | 대기 | 누적 |
|---|---|---|
| 1 | 즉시 | 0s |
| 2 | 30s | 30s |
| 3 | 2m | 2.5m |
| 4 | 10m | 12.5m |
| 5 | 1h | ~1.2h |
| 6+ | `dead` | |

**검증할 것**

| 질문 | 측정 방법 | 결과 |
|---|---|---|
| 몇 번째 시도에서 대부분 성공하는가 | `dispatch_log`의 `attempt` 분포 | ☐ |
| 30초가 적절한가, 너무 짧은가 | 매체 장애 주입 후 회복 시각 관측 | ☐ |
| `dead` 컷을 6회로 두면 유실률은 | 최종 실패 건수 ÷ 전체 | ☐ |
| 지터(jitter)가 필요한가 | 동시 재시도 몰림 관측 | ☐ |

> **"왜 이 값인지"를 실험으로 정한다**는 것이 이 문서의 목적이다. 공공데이터 API에서 1,000번째 요청의 예외를 200ms 지연으로 해결했던 것과 같은 방식이다.

## 7. 기록 규칙

- `EXPLAIN` 결과는 **원문 그대로** 붙인다. 요약하지 않는다
- 측정은 **3회 이상**, p50·p95를 함께 적는다. 평균만 적지 않는다
- 예상과 다르면 **예상을 지우지 말고 둘 다 남긴다**
- 개선 전후를 비교할 때는 **한 번에 한 가지만** 바꾼다
