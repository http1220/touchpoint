# 실제 사고 중 이 프로젝트에서 테스트 코드로 구현 가능한 사례

> 2026-09-16 · 원본 조사 → [payment-incidents.md](payment-incidents.md)
>
> 사고 15건 중 **이 코드베이스에서 테스트 코드로 재현·고정할 수 있는 것만** 추렸다.
> 데이터센터 화재·스위치 고장처럼 인프라 자체가 원인인 사고는 뺐다(맨 아래).

## 판정 기준

| 표시 | 뜻 |
|---|---|
| ✅ **있음** | 같은 실패 모양을 막는 단위 테스트가 이미 저장소에 있다 |
| 🟡 **단위 가능** | DB 없이 `src/` 순수 로직 + PHPUnit 으로 새로 만들 수 있다 |
| 🔵 **DB 통합 필요** | 동시성·트랜잭션·UNIQUE 처럼 **MySQL 이 판정하는** 부분. 지금 테스트 기반(PHPUnit)에는 DB 가 없어 **운영 서버 스크립트로만 실측**했다. CI 에 MySQL 서비스 컨테이너를 붙이면 테스트 코드가 된다 |

> **지금 저장소의 한계부터.** PHPUnit 396건은 전부 DB·프레임워크 없이 돈다. 결제 중복을 실제로 막는 조건부 UPDATE·`INSERT IGNORE`+UNIQUE·`SKIP LOCKED` 는 **테스트 코드가 아니라 [failure-scenarios.md](../failure-scenarios.md) D-1·D-3 의 서버 실측**으로만 확인돼 있다. 아래 🔵 가 그 빈칸이다.

## 1. 실패 뒤 재시도가 중복·폭주를 만든다 — Visa(5) · UPI(3)

**사고의 모양** Visa 는 실패 응답을 받은 사용자가 다시 결제해 승인이 여러 번 잡혔다. UPI 는 결과를 모르는 은행들이 상태 조회를 간격 없이 쏟아 중앙 시스템을 막았다.

### ✅ 이미 있는 테스트

| 테스트 | 막는 것 |
|---|---|
| `BackoffPolicyTest::시도_횟수마다_정해진_간격을_돌려준다` | 즉시 재시도 금지. 30초 → 2분 → 10분 → 1시간 → 3시간 |
| `BackoffPolicyTest::최대_시도를_넘으면_포기한다` | UPI 의 "최대 3회" 에 해당하는 **상한** |
| `BackoffPolicyTest::지터가_커도_즉시_재시도로_무너지지_않는다` | 여럿이 같은 순간 몰려 재시도하는 것 방지 |
| `BackoffPolicyTest::응답에_따라_재시도_여부를_정한다` | 4xx 는 재시도하지 않는다 — 고칠 것은 요청이다 |
| `MetaChannelTest::test_HTTP_400_이어도_레이트리밋_코드면_재시도한다` | 매체의 "잠깐 기다려" 를 영구 실패로 버리지 않기 |
| `WebhookSignatureTest::test_재생_창은_양쪽으로_닫힌다` | 오래된 요청의 재전송 차단 |
| `DedupKeyTest::같은_입력은_항상_같은_키를_만든다` | 같은 전환은 같은 중복 제거 키 |

### 🟡 새로 만들 수 있는 단위 테스트

- **재시도 총 소요 시간 상한** — 사다리 합계(약 4시간 42분)가 매체의 이벤트 수용 기한(Meta 7일)보다 짧다는 것을 테스트로 고정. 사다리를 늘리는 변경이 "보내 봐야 거절될 재시도" 를 만들면 깨진다.

### 🔵 DB 통합 테스트가 필요한 것

- **같은 웹훅 동시 N개 → 전이 1 · 코인 1** — `Payment_model::applyEvent` 의 조건부 UPDATE. 지금은 D-3 서버 실측(동시 8개)뿐.
- **같은 `idempotency_key` 로 `/purchase` 동시 N개 → 결제 1행** — `INSERT IGNORE` + `uq_idem`.
- **대조군**(`PAYMENT_WEBHOOK_PRECHECK=true` + 지연)이 **실제로 코인을 두 번 지급하는지**도 같이 고정해야 한다. 대조군이 조용히 안전해지면 본 테스트가 무엇을 증명하는지 흐려진다.

## 2. 같은 작업이 두 번 실행된다 — 토스(12) · Santander(13)

**사고의 모양** 예약·자동이체가 스케줄링·프로그램 변경 오류로 두 번 실행돼 이중 출금·이중 지급.

### ✅ 이미 있는 테스트

| 테스트 | 막는 것 |
|---|---|
| `PaymentStateMachineTest::test_같은_상태로는_전이하지_않는다` | captured → captured 가 표에 없다 = 두 번째 실행은 무시 |
| `PaymentStateMachineTest::test_종결_상태에서는_아무_데도_못_간다` | refunded 뒤의 모든 전이 차단 |
| `PaymentStateMachineTest::test_역행은_막힌다` | 늦게 온 이전 단계 이벤트가 상태를 되돌리지 않음 |
| `RefundPolicyTest::test_캡처_전에_온_환불만_재시도를_요청한다` | 순서가 뒤집힌 환불을 무시하지 않고 재전송 요청 |

### 🟡 새로 만들 수 있는 단위 테스트 — **조사 중 발견한 빈틈**

`RefundPolicy::revocation(amount, remaining)` 은 **멱등하지 않다.**

```
첫 환불   revocation(100, 100) → 회수 100 · 사용 0     ← 맞다
두 번째   revocation(100,   0) → 회수   0 · 사용 100   ← "100 을 썼다" 로 잘못 보고
```

지금은 `applyEvent` 의 조건부 UPDATE 가 두 번째 `onRefunded` 를 막아서 사고가 안 난다. 즉 **안전이 DB 한 줄에만 걸려 있다.** 토스·Santander 처럼 "두 번 실행" 이 한 번이라도 새면 코인 사용 불일치 경보가 거짓으로 뜬다.

- 테스트로 고정할 것: 회수 결과에 **"이미 회수됨"** 을 구분하는 값(예: lot 에 회수 시각)을 두고, 두 번째 호출이 `사용 100` 이 아니라 **`이미 회수됨`** 을 돌려주는지.

### 🔵 DB 통합 테스트가 필요한 것

- **워커 4개가 같은 아웃박스를 동시에 선점해도 전송 1회** — `FOR UPDATE SKIP LOCKED`. 지금은 D-1 실측(2,000건 · 중복 0)뿐.
- **`SKIP LOCKED` 를 꺼도 중복이 0인지** — 막는 것이 SKIP LOCKED 가 아니라 "선점과 상태 변경이 한 트랜잭션" 이라는 D-1 결론을 테스트로.

## 3. 출금은 됐는데 반대편 기록이 없다 — 카카오페이(4)

**사고의 모양** 계좌 출금 기록은 있는데 송금 내역·수취인 입금이 없다. 피해 규모를 사후에 파악하지 못했다.

**이 프로젝트의 같은 모양** 결제가 `captured` 인데 ① 코인 lot 이 없거나 ② 구매 전환이 없거나 ③ 아웃박스 행이 없다. 반대로 ④ 코인은 있는데 결제가 captured 가 아니다.

### ✅ 이미 있는 테스트 (매체 쪽 대사)

| 테스트 | 막는 것 |
|---|---|
| `ReconciliationTest::test_보냈는데_없으면_누락이다` | 보낸 전환이 GA4 에 없음 |
| `ReconciliationTest::test_안_보냈는데_있으면_초과다` | 보낸 적 없는 것이 집계됨 |
| `ReconciliationTest::test_한_건이_두_번_세어지면_중복이다` | 중복 집계 |

### 🟡 새로 만들 수 있는 단위 테스트 — **결제 내부 대사**

매체 쪽 대사는 있는데 **결제 ↔ 코인 ↔ 전환 사이의 대사는 없다.** 같은 모양의 순수 함수(`src/Payment/Reconciliation`)로 만들면 DB 없이 테스트할 수 있다.

| 입력 | 기대 판정 |
|---|---|
| captured 결제 · lot 1 · 전환 1 | 정상 |
| captured 결제 · lot 0 | **코인 미지급** (카카오페이의 "출금됐는데 미입금") |
| captured 결제 · 전환 0 | **매체 미보고** |
| lot 있음 · 결제 authorized | **대가 없는 지급** |
| refunded 결제 · lot remaining > 0 | **회수 누락** |
| captured 결제 · 상품표에 없는 금액 | **사람이 메워야 할 건** (지금은 error 로그 한 줄뿐) |

## 4. 늦은 것과 사라진 것을 구분 못 한다 — Zelle(11) · Wells Fargo(15)

**사고의 모양** 은행은 "사라진 게 아니라 지연" 이라 했지만 고객은 구분할 수 없었다.

**이 프로젝트에서 이미 한 번 겪었다.** GA4 반영률을 +25시간에 "4.8% 영구 유실" 로 오판했고 +40시간에 100% 였다 → [benchmarks.md 5-1](../benchmarks.md)

### ✅ 이미 있는 테스트

- `ReconciliationTest::test_204를_받아도_집계되지_않을_수_있다` — "보냄" 과 "반영" 을 다른 값으로.

### 🟡 새로 만들 수 있는 단위 테스트 — **오판을 코드로 막기**

지금 `Reconciliation` 은 시각을 모른다. 없으면 무조건 "누락" 이다.

- 입력에 **보낸 시각 · 관측 시각 · 처리 창(GA4 48시간)** 을 넣고,
  - 창 안이면 **대기**, 창을 넘기면 **누락**
  - `+25h 에 95.2%` 입력 → 판정 **"대기 중 4.8%"** 이지 "누락 4.8%" 가 아니어야 한다
- 테스트 이름이 곧 그 오판의 기록이 된다.

### ✅ 이미 있는 테스트

- `MetaChannelTest::test_5xx_와_연결_실패는_재시도한다`

## 8. 롤백이 두 번째 사고가 된다 — RBS(9)

**사고의 모양** 문제가 난 업그레이드를 **테스트 없이 제거**해 더 꼬였다.

### 🔵 DB 통합 테스트가 필요한 것

- **마이그레이션 `up → down → up` 왕복** — 마이그레이션 12개 모두 `down()` 이 있지만 **CI 에서도 작업 기록에서도 실행한 흔적이 없다.** 빈 DB 에서 최신까지 올리고, 한 단계씩 내렸다 다시 올려 스키마가 같은지 비교.
- 최근 추가한 `payment_client_context`(FK CASCADE)·`collect_events` 확장(UNIQUE 추가)은 `down()` 순서가 틀리면 FK 때문에 실패한다 — 롤백이 필요한 순간에 처음 알게 되는 종류다.

## 우선순위 제안

| 순 | 무엇 | 종류 | 이유 |
