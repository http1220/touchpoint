# 실패 시나리오

> **상태: 범위 안 12건 중 10건 실측** (B-1 · B-2 · B-3 · C-1 · C-2 · C-3 · D-1 · D-2 · E-1 · E-2. B-3 은 부분). 나머지는 시나리오와 **검증 방법**까지만 확정했고, `결과`·`대응` 열은 실제로 재현한 뒤 채운다.
> 이 문서와 [benchmarks.md](benchmarks.md)가 이 저장소의 진짜 차별점이다. 코드는 누구나 쓴다.

기록 규칙:

- **재현 절차를 먼저 적고**, 그다음 결과를 적는다. 결과부터 적으면 재현 불가능한 문서가 된다
- 예상과 다르면 **예상을 고치지 말고 둘 다 적는다.** 틀린 예상이 배운 지점이다
- 스크린샷·`curl` 출력·`EXPLAIN`은 원문 그대로 붙인다

## A. 쿠키 — 범위에서 뺀 구간

**A-1·A-2는 하지 않는다.** 등록 도메인을 1개로 정했기 때문이다 → [ADR-018](decisions/ADR-018-single-registered-domain.md)
설계와 이유는 남겨 둔다. 못 한 것과 모르는 것은 다르다.

### A-1. 서드파티 쿠키 차단 — 브라우저별 ✗ 범위 밖

원래 계획은 Chrome(기본/차단ON/`Partitioned`) · Safari(ITP) · Firefox(TCP)에서 first-party 쿠키와 third-party 쿠키의 전송 여부를 나란히 재는 것이었다.

**성립하지 않는 이유**: 브라우저는 same-site를 **eTLD+1**로 판정한다. `lp.sshwan.com` → `api.sshwan.com`은 같은 사이트이므로 서드파티 쿠키 차단이 **발동할 조건 자체가 없다.** 서브도메인으로는 흉내도 되지 않는다.

> 2025년 현황만 적어 둔다 — Chrome은 서드파티 쿠키 폐지를 **철회**했고(2024-07, 2025-04), Privacy Sandbox는 2025-10-17에 종료됐다. Safari·Firefox는 계속 차단한다. **그래서 이 문제는 "사라지는 문제"가 아니라 "브라우저 편차 문제"다.** 이 인식은 조사에서 얻은 것이고 도메인과 무관하게 유효하다.

### A-2. `SameSite` 설정 누락 ✗ 범위 밖

`SameSite=None`이 필요한 상황은 cross-site 요청에서만 생긴다. same-site에서는 `Lax`로 충분하므로 **실패가 일어나지 않는다.**

`Partitioned`(CHIPS) 역시 `SameSite=None; Secure`와 함께여야 효력이 있으므로 같이 빠진다.

### A-3. same-site · cross-origin 대조 ✅ 이건 한다

| 호출 | 사이트 | 오리진 | 쿠키 | CORS | 결과 |
|---|---|---|---|---|---|
| `lp.sshwan.com` → `app.sshwan.com` | 같음 | 같음(호스트만 다름) | `Lax`로 전송 | **적용됨** | ☐ |
| `lp.sshwan.com` → `api.sshwan.com` | 같음 | **다름** | `Lax`로 전송 | **적용됨** | ☐ |

> **이 표가 [ADR-018](decisions/ADR-018-single-registered-domain.md)의 요지다.** 사이트가 같아도 오리진이 다르면 CORS는 그대로 걸린다. "크로스사이트가 아니면 CORS도 없다"는 흔한 오해이고, 나도 처음에 그렇게 묶어서 잃는 시나리오를 4개로 과대평가했다. 실제로는 2개다.

## B. CORS

측정 환경: `lp.sshwan.com` → `api.sshwan.com` (same-site, **cross-origin**), Chromium, 2026-09-12.

### B-1. preflight 발생 조건 ✅ 실측

| 요청 | preflight | 결과 |
|---|---|---|
| `fetch` + `Content-Type: application/json` | **발생** | ✅ `OPTIONS /collect → 204` |
| `navigator.sendBeacon` (`text/plain` 고정) | 없음 | ✅ `POST` 만 기록됨 |
| 같은 `fetch` 를 10분 안에 재호출 | **없음** | ✅ `Access-Control-Max-Age: 600` 이 먹는다 |

엣지 로그(JSON)에서 메서드만 뽑은 것이다. 브라우저 DevTools 가 아니라 **서버 쪽 기록**이라 조작 여지가 없다.

```
OPTIONS /collect → 204     page_view (fetch) — 첫 요청이라 preflight
POST    /collect → 200     page_view 본 요청
POST    /collect → 200     click (fetch) — preflight 캐시되어 OPTIONS 없음
POST    /collect → 200     click (beacon) — 애초에 preflight 없음
```

> **세 번째 줄이 `Max-Age` 의 값어치다.** 이게 없으면 수집 한 건마다 왕복이 두 번이다.

---

### B-2. `Allow-Origin: *` 로 바꾸면 ✅ 실측 — **가장 중요한 발견**

`.env` 의 `CORS_ALLOW_ORIGIN_WILDCARD=true` 로 일부러 깨진 조합을 내보냈다.

**브라우저 콘솔 원문**

```
Access to fetch at 'https://api.sshwan.com/collect' from origin 'https://lp.sshwan.com'
has been blocked by CORS policy: The value of the 'Access-Control-Allow-Origin' header
in the response must not be the wildcard '*' when the request's credentials mode is 'include'.
```

여기까지는 예상대로다. **그런데 같은 시각 DB 를 보니 그 요청이 기록돼 있었다.**

```
id  event      transport  received_at
 7  page_view  fetch      2026-09-12 08:18:04.748   ← 브라우저가 "차단" 한 그 요청
```

| | |
|---|---|
| **CORS 는 요청을 막지 않는다** | 요청은 서버에 도달했고 처리됐다. 막히는 것은 **응답을 읽는 것**이다 |
| **스크립트는 이유를 모른다** | `catch` 에 온 것은 `TypeError: Failed to fetch` 뿐이다. CORS 라는 말이 없다 |
| **그래서 재시도하면 중복된다** | 클라이언트는 실패로 알고 다시 보내는데 서버에는 이미 들어가 있다 |

```js
// track.js 가 실제로 받은 것
[touchpoint] collect 오류 TypeError: Failed to fetch
```

> **이것이 이 실험의 진짜 산출물이다.** *"`*` 와 credentials 는 같이 못 쓴다"* 는 문서를 읽으면 안다. **그 설정으로 데이터가 어떻게 오염되는지**는 해 봐야 안다 — 수집은 되는데 클라이언트는 실패로 알고, 재시도가 붙으면 전환이 부풀려진다.
>
> 실무에서 이 조합은 "CORS 가 안 되네" 하고 `*` 로 바꿨다가 생긴다. 증상이 "데이터가 없음" 이 아니라 **"데이터가 두 배"** 라서 원인을 CORS 로 의심하지 않게 된다.

| 설정 | 결과 |
|---|---|
| `Allow-Origin: *` + `credentials: 'include'` | ✅ 브라우저 차단 · **서버는 기록함** |
| 정확한 오리진 + `Allow-Credentials: true` | ✅ 정상 |
| 오리진 반향 + `Vary: Origin` 누락 | ☐ 중간 캐시가 필요해 미측정. 정책 코드에는 `Vary` 를 강제하고 테스트로 못박아 뒀다 |

### B-3. `sendBeacon` 트레이드오프 ◐ 부분 실측

| 항목 | `fetch` | `sendBeacon` | 결과 |
|---|---|---|---|
| preflight | 발생 | 없음 | ✅ B-1 참조 |
| 커스텀 헤더 | 가능 | **불가** | ✅ `Content-Type` 도 `text/plain` 고정 |
| **CORS 오설정 시** | **차단** | **통과** | ✅ 아래 |
| 페이지 이탈 중 전송 | 취소될 수 있음 | **보장** | ☐ 100회 반복 측정 미실시 |
| 페이로드 크기 | 큼 | 약 64KB | ☐ |

**세 번째 줄이 예상 밖이었다.** B-2 의 와일드카드 상태에서 `fetch` 는 전부 막혔는데 `sendBeacon` 은 그대로 들어왔다.

```
id  event  transport  received_at                 상태
 8  click  beacon     2026-09-12 08:18:20.760     와일드카드 ON 중 — 통과
```

이유는 단순하다. **`sendBeacon` 은 응답을 읽지 않는다.** 읽지 않으므로 브라우저가 CORS 로 막을 이유가 없다. 반대로 말하면 **성공했는지 확인할 방법도 없다** — `navigator.sendBeacon()` 의 반환값은 "큐에 넣었다" 는 뜻이지 "서버가 받았다" 가 아니다.

> 트레이드오프가 이렇게 갈린다.
> **`fetch`** 는 결과를 알 수 있지만 CORS 에 걸리고 이탈 중 취소된다.
> **`sendBeacon`** 은 잘 나가지만 나갔는지 알 수 없다.
> 수집 파이프라인이 서버 큐(아웃박스)를 두는 이유가 여기에도 있다 — **클라이언트 전송은 어느 쪽이든 확인이 안 된다.**

## C. 리다이렉트

### C-1. 301 vs 302 ✅ 실측

측정 환경: `lp.sshwan.com/go` → `/l/8733`, Chromium, 2026-09-12.
같은 URL 을 숨긴 iframe 으로 연속 로드한 뒤, 엣지 접근 로그에서
`pid=` 마커를 세어 **몇 번이나 서버까지 왔는가**를 재었다.

| # | 상태 | 캐시 헤더 | 브라우저 로드 | 서버 도달 | |
|---|---|---|---|---|---|
| a | 302 | `no-store` | 2 | **2** | ✅ 기본값 |
| b | 301 | `no-store` | 2 | **2** | ✅ `no-store` 가 이긴다 |
| c | 301 | 없음 | 3 | **1** | ✅ 다시 오지 않는다 |
| d | 302 복구 후 **c 와 같은 URL** | `no-store` | 2 | **0** | ✅ 고쳐도 안 돌아온다 |
| e | 302 복구 후 새 URL | `no-store` | 2 | **2** | ✅ 서버는 멀쩡하다 |

엣지 로그 원본 — `/go` 가 찍힌 순간만 뽑았다.

```
12:38:39  302  /go?work=8733&pid=c1a302store     a ①
12:38:41  302  /go?work=8733&pid=c1a302store     a ②
12:39:16  301  /go?work=8733&pid=c1b301store     b ①
12:39:18  301  /go?work=8733&pid=c1b301store     b ②
12:41:34  301  /go?work=8733&pid=c1c301nocache   c ①  ← c 의 ②③ 은 여기 없다
12:50:25  302  /go?work=8733&pid=c1d302after     e ①  ← d 의 ①② 도 없다
12:50:27  302  /go?work=8733&pid=c1d302after     e ②
```

**세 가지를 알았다.**

**① 301 자체는 범인이 아니다.** b 를 보면 301 에 `no-store` 를 붙이면
두 번 다 서버에 온다. 위험한 것은 **캐시 헤더 없는 301** 이다.
"301 은 쓰지 마라" 보다 "영구 캐시를 허용하지 마라" 가 맞는 규칙이다.

**② 그런데 c 를 재현하는 데 한 차례 걸렸다.**
브리지가 붙이던 `no-store` 를 떼냈는데도 응답에 그대로 남아 있었다.
범인은 PHP 였다.

```
session.cache_limiter = nocache   (PHP 기본값, session.cache_expire = 180)
→ Expires: Thu, 19 Nov 1981 08:52:00 GMT
  Cache-Control: no-store, no-cache, must-revalidate
  Pragma: no-cache
```

세션을 쓰는 모든 응답이 자동으로 캐시 불가가 된다. 즉 **브리지가
붙이던 `no-store` 는 처음부터 중복이었다.** 실험을 성립시키려고
`header_remove()` 로 세 줄을 걷어낸 뒤에야 c 가 재현됐다.

> 이게 실측의 값어치다. 코드에도 `no-store` 가 있었고 응답에도 `no-store` 가
> 있었지만, **둘은 같은 줄이 아니었다.** 지워 보기 전에는 알 수 없었다.

**③ d 가 이 장의 결론이다 — 301 은 롤백이 안 된다.**
c 로 한 번 캐시된 뒤에 서버를 302 + `no-store` 로 되돌리고
**같은 URL 을 두 번 더 불렀는데 서버에 한 번도 오지 않았다.**
같은 순간 새 URL(e)은 두 번 다 들어왔으니 서버 쪽은 멀쩡하다.

보통의 사고는 고치면 멈춘다. 이건 고쳐도 **이미 응답을 받아 간
브라우저들은 돌아오지 않는다.** 캐시가 만료되거나 사용자가 직접
지우기 전까지, 그만큼의 광고 클릭이 영원히 집계되지 않는다.
캐시 헤더 없는 301 의 유효기간은 휴리스틱이라 **언제 끝나는지도 모른다.**

그래서 브리지는 302 로 고정하고, 실험 스위치는 `.env` 에만 남겨 둔다.

```bash
BRIDGE_REDIRECT_STATUS=302      # 301 로 바꾸면 c·d 재현
BRIDGE_CACHE_CONTROL=no-store   # 비우면 세션이 붙인 헤더까지 걷어낸다
```

**남겨 둔 한계.** 클릭을 세는 전용 테이블이 없어 이번엔 엣지 로그로 셌다.
`touchpoints` 는 `UNIQUE (visit_id, position)` 로 방문당 first/last 둘만 두므로
클릭 수를 보존하지 않는다 — 의도한 설계이지만, 그래서 "몇 번 클릭됐는가" 는
DB 가 아니라 로그에 물어야 한다.

### C-2. 리다이렉트 중 파라미터 유실 ✅ 실측

브리지가 유입 파라미터를 목적지까지 넘기는 방식이 둘이다
(`BRIDGE_PARAM_MODE`, 요청의 `?mode=` 가 이긴다).

```
A. passthru   /l/8733?pid=..&utm_source=..&gclid=..   화이트리스트만 전달
B. vid        /l/8733?vid=<32자 hex>                   방문 식별자만 전달 (기본값)
```

**묻는 것은 하나다 — 사용자가 주소창을 복사해 남에게 보내면 어떻게 되는가.**
방문자1 은 브리지를 타고 들어오고, 방문자2 는 **쿠키 없이** 그 URL 을 그대로 연다.
`curl` 두 개에 쿠키 항아리를 따로 준 것이 전부다.

```
=== A. passthru ===
방문자1 이 받은 목적지:
  /l/8733?pid=c2A&utm_source=c2A&utm_medium=cpc&gclid=GCLID_C2A
방문자2(쿠키 없음) 가 그 URL 을 그대로 연다:  HTTP 200
  방문자2 가 받은 쿠키: 01a095b075567fb0…            ← 새 방문이다

=== B. vid ===
방문자1 이 받은 목적지:
  /l/8733?vid=01a095b0759d74c7b74237264ef4c4a7
방문자2(쿠키 없음) 가 그 URL 을 그대로 연다:  HTTP 200
  방문자2 가 받은 쿠키: 01a095b0759d74c7b74237264ef4c4a7  ← 방문자1 의 것
```

DB 쪽 결과. 광고 클릭은 **양쪽 다 한 번**이었다.

| 방식 | 생긴 방문 | 캠페인이 붙은 방문 |
|---|---|---|
| A. passthru | 498(방문자1) · **499(방문자2)** | **2건** |
| B. vid | 500(방문자1, 방문자2 흡수) | **1건** |

```
| pid  | visit_id | landing_path                                            |
| c2a  |      498 | /go?work=8733&pid=c2A&…&mode=passthru                   |
| c2a  |      499 | /l/8733?pid=c2A&utm_source=c2A&utm_medium=cpc&gclid=…   |  ← 공유로 생긴 유입
| c2b  |      500 | /go?work=8733&pid=c2B&…&mode=vid                        |
```

**A 는 유입을 부풀린다.** 클릭 한 번이 유입 두 건이 됐다. 링크가 단톡방에
올라가면 배수가 커진다. 매체가 청구하는 클릭 수와 자체 집계가 벌어지는데,
**자체 집계 쪽이 더 크다** — 대개 매체를 의심하게 되는 방향이라 원인 찾기가 늦어진다.

**B 는 부풀지 않는다. 대신 두 사람이 한 방문이 된다.**
이건 `BridgeDestination` 의 docblock 이 "그 일이 일어나지 않는다" 고
적어 둔 부분인데, 재 보니 **절반만 맞았다.** 건수는 늘지 않지만
방문자2 는 방문자1 의 쿠키를 그대로 받아 갔다. 이후 방문자2 가 무엇을 하든
그건 방문 500 의 기록이다.

이어서 방문자2 가 광고 없이 `/l/8733` 을 직접 열어 봤다. **접점은 그대로였다.**

```
| visit_id | position | pid  | occurred_at             |
|      500 | last     | c2b  | 2026-09-12 12:56:04.771 |   ← 직접 방문이 덮지 않았다
```

`TouchpointResolver` 규칙 3("직접 유입은 소스를 덮지 않는다") 이 의도대로
동작한 것이다. 광고 기여가 사라지지 않게 하려고 넣은 규칙인데,
**공유로 흡수된 사람에게는 반대로 작동한다** — 벗어날 방법이 없다.

> **결론: 둘 다 틀리고, 틀리는 방향이 다르다.**
> A 는 **건수**를 틀리고, B 는 **사람**을 틀린다.
> 정산이 걸린 쪽은 건수라서 기본값은 B 로 둔다. 그리고 B 의 값은
> 방문 식별자 하나뿐이라 — 권한도, 개인정보도, 잔액도 붙어 있지 않다 —
> 남의 것을 주워도 할 수 있는 일이 "이미 있는 방문에 접점을 갱신한다" 로 끝난다.
> 세션 식별자였다면 이 선택은 성립하지 않는다.

**남겨 둔 것.** 전환까지 이어 보려면 `/conversion` 엔드포인트가 필요한데
아직 컨트롤러가 없다(라우트만 있다). 흡수된 방문자2 의 결제가 c2B 로
귀속되는 것까지가 이 시나리오의 끝인데, 거기는 아직 [추정] 이다.

### C-3. 오픈 리다이렉트 ✅ 실측

시나리오를 적을 때는 `/go?return=<목적지>` 를 막는 실험으로 잡아 뒀다.
막상 재려고 보니 **브리지에 `return` 같은 파라미터가 없다.** 목적지는
`work` 하나로 서버가 조립한다.

> 그래서 첫 결과는 "막았다" 가 아니라 **"막을 것이 없다"** 였다.
> 오픈 리다이렉트를 없애는 가장 확실한 방법은 검증을 잘하는 게 아니라
> **목적지를 입력으로 받지 않는 것**이다.

그런데 목적지의 **앞부분**은 여전히 입력에서 온다.

```php
$base = 'https://'.$this->server('HTTP_HOST');   // Bridge::go()
```

`Host` 헤더다. 여기가 이 장의 진짜 과녁이다. 12가지를 던져 봤다.

| 입력 | 코드 | Location | 막은 층 |
|---|---|---|---|
| `work=8733` | 302 | `https://lp.sshwan.com/l/8733?vid=…` | (정상) |
| `Host: m.sshwan.com` | 302 | `https://m.sshwan.com/l/8733?vid=…` | (정상 — 온 호스트로 돌려보낸다) |
| `work=abc` | **400** | — | `BridgeDestination::work()` |
| `work=` (빈값) | **400** | — | 〃 |
| `work` 없음 | **400** | — | 〃 |
| `work=../../etc/passwd` | **400** | — | 〃 |
| `work=8733%0d%0aX-Injected:%20yes` | **400** | — | 〃 (헤더 분할) |
| `work=999999999999999999999` (19자리) | **400** | — | 〃 (1~18자리) |
| `return=https://evil.example` | 302 | `…/l/8733?vid=…` | **그런 파라미터가 없다** |
| `return=//evil.example` | 302 | `…/l/8733?vid=…` | 〃 |
| `Host: evil.example` | 302 | `https://lp.sshwan.com/go?work=8733` | **엣지 443 기본 블록** |
| `Host: lp.sshwan.com.evil.example` | 302 | `https://lp.sshwan.com/go?work=8733` | 〃 |
| `Host: api.sshwan.com` | **404** | — | `MY_Controller::requireHost()` |

**400 본문은 입력을 되비추지 않는다.** `<script>` 를 섞어 던져도
고정 문구만 돌아온다.

```json
{"type":"https://sshwan.com/problems/invalid-target","title":"invalid-target",
 "status":400,"detail":"목적지를 만들 수 없습니다: 작품 ID 가 올바르지 않습니다.",
 "trace_id":"8fbeb057fd48847a9c92187550153ed3"}
```

**막은 층이 둘이고, 엣지 로그가 어느 쪽인지 알려 준다.**

```
host":"evil.example"      … "status":302, "rt":0.000, "read_target":""      ← PHP 미도달
host":"api.sshwan.com"    … "status":404, "rt":0.018, "read_target":"rdb1"  ← PHP 도달
```

`rt=0.000` 과 빈 `read_target` 이 "엣지에서 끝났다" 는 증거다.
모르는 Host 는 PHP 를 아예 못 본다. 반대로 `api.` 는 **아는 Host 라서**
PHP 까지 갔고, 거기서 `requireHost(array('lp','m'))` 가 404 를 냈다.
같은 "거부" 지만 비용도 위치도 다르다.

**그런데 여기서 하나 걸렸다 — 앞의 방어가 우연이었다.**
443 에는 `default_server` 가 없었다. 모르는 Host 가 막힌 건 nginx 가
매칭 실패 시 **그 포트의 첫 서버 블록**을 고르는데, 마침 첫 블록이
루트 도메인 블록이었고 그 안의 `return 302` 가 목적지를 하드코딩하고
있었기 때문이다.

```nginx
return 302 https://lp.${SHOP_DOMAIN}$request_uri;   # Host 가 무엇이든 결과가 같다
```

동작은 맞지만 **블록 순서에 기댄 보장**이다. 누가 서버 블록을 위로
하나 옮기면 조용히 사라진다. `listen 443 ssl default_server` 로 명시했다.

> 이 장에서 배운 게 두 개다.
> **① 시나리오가 틀릴 수 있다.** `return=` 을 막는 실험을 준비했는데
> 정작 위험한 입력은 쿼리스트링이 아니라 `Host` 헤더였다.
> **② 되고 있다고 해서 의도한 것은 아니다.** 통과하는 테스트를 보고
> "막혀 있구나" 하고 넘어갔으면 순서 의존을 못 봤을 것이다.

**남겨 둔 것.** `Host` 가 틀렸을 때 302 로 정규 호스트에 넘기는 게 맞는지는
논쟁거리다. `421 Misdirected Request` 나 `444`(연결 종료) 가 더 정직하다.
지금은 랜딩 도메인이라 넘기는 쪽을 택했고, 수집 도메인(`api.`)은
애초에 `requireHost` 가 404 를 낸다.

## D. 매체 전송 · 워커

### D-1. 워커 중복 실행 ✅ 실측 — **예상이 틀린 곳**

켠 쪽은 [benchmarks.md 2장](benchmarks.md)에 있었다. 없던 것은 **끈 쪽**이라
`OUTBOX_SKIP_LOCKED` 스위치를 만들어 대조군을 돌렸다.
워커 4개, `NoopChannel`(네트워크 제거), 같은 서버·같은 시각대.

처리량은 `sent_at` 의 최소~최대 폭으로 잰다. 컨테이너 기동 시간이
벽시계에 섞이지 않게 하려는 것이다.

| 배치 | `SKIP LOCKED` | 건수 | 소요 | 초당 | 중복 `(outbox_id, attempt)` |
|---|---|---|---|---|---|
| 100 | **켬** | 2000 | 10.13초 | 197 | **0** |
| 100 | 끔 | 2000 | 8.59초 | 233 | **0** |
| 5 | **켬** | 999 | 6.49초 | 154 | **0** |
| 5 | 끔 | 1000 | 6.11초 | 164 | **0** |

**예상은 "끄면 락 대기로 처리량 급감" 이었다. 급감하지 않았다.
오히려 끈 쪽이 매번 조금 빨랐다.**

경합이 없어서 그런 건 아니다. 켠 쪽 워커 로그를 보면 **실제로 건너뛰고 있다.**

```
[13:10:53.537] #10610 noop attempt=1 → sent
[13:10:53.553] #10612 noop attempt=1 → sent      ← 10611 은 남이 잠갔다
[13:10:53.569] #10614 noop attempt=1 → sent
[13:10:53.579] #10616 noop attempt=1 → sent
```

행이 잠겨 있었고 SKIP LOCKED 가 제 일을 했다. 그런데도 이득이 없었다.
**잠금을 쥐고 있는 시간이 너무 짧기 때문이다.** 선점 트랜잭션 안에는
`SELECT … FOR UPDATE` 와 `UPDATE … SET status='sending'` 둘뿐이고,
외부 HTTP 는 트랜잭션 **밖**에 있다(→ `cli/Dispatch::handle` 의 ③).
대기가 마이크로초 단위면 줄을 서는 쪽이 더 싸다 — 건너뛰려면
인덱스를 더 훑어야 하니까.

> **그래서 SKIP LOCKED 는 이 구성에서 처리량을 벌어 주지 않는다.
> 보험이다.** 보험료가 0 에 가까울 뿐이다.
> 값을 하는 조건은 **잠금 구간이 길어질 때**인데, 그건 전송을
> 트랜잭션 안에 넣었을 때 벌어진다. 이 프로젝트는 그러지 않기로 했으므로
> (→ [ADR-004](decisions/ADR-004-skip-locked.md)) 두 결정이 서로를 상쇄한 셈이다.
>
> 반대로 말하면, **전송을 트랜잭션 안에 넣는 순간 SKIP LOCKED 가 필수가 된다.**
> 그 조합은 아직 안 돌려 봤다 — [추정]이다.

**중복은 네 번 모두 0이었다.** 끄든 켜든 중복 전송은 없다.
SKIP LOCKED 는 중복을 막는 장치가 아니라 **기다릴지 건너뛸지**를 정할 뿐이고,
중복을 막는 것은 잠금 자체와 "선점과 상태 변경이 한 트랜잭션" 이라는 규칙이다.
이걸 헷갈리면 SKIP LOCKED 를 정합성 장치로 소개하게 된다.

#### 곁가지로 잡힌 것 — 좀비 회수가 실제로 돌았다

처음 잰 `batch=5 / 켬` 값은 **93.3초**였다. 끈 쪽(7.5초)의 12배라
"SKIP LOCKED 가 12배 느리다" 로 적을 뻔했다.

원인은 다른 데 있었다. 그 회차에만 워커 프로세스가 다섯 개
(`trace_id` 5개, `--scale worker=4` 인데) 찍혀 있었다 — 하나가 전송 중에 죽은 것이다.

```
| id   | attempt | status | claimed_at              | sent_at                 |
| 8613 |       2 | sent   | 2026-09-12 13:09:25.486 | 2026-09-12 13:09:25.495 |
```

**1000건 중 정확히 한 건만 `attempt=2`** 였다. 나머지 999건은
13:07:53.281 ~ 13:07:59.768 사이에 끝났고(6.5초), 이 한 건만
**85.7초 뒤**에 나갔다. 내 측정 루프가 `pending|sending` 이 0이 되기를
기다리고 있었으니, 잰 것은 처리량이 아니라 **좀비 회수 대기 시간**이었다.

```php
// cli/Dispatch::work()
$this->outbox_model->reclaimZombies(DISPATCH_TIMEOUT_MS/1000 * 10 + 60);  // = 90초
```

의도한 값이 그대로 나왔다. 계획에 없던 측정이지만
**워커가 죽어도 행이 조용히 사라지지 않는다**는 것이 운영 중에 확인됐다.

> 배운 것은 회수가 동작한다는 사실보다 **평균 하나만 보면 안 된다**는 쪽이다.
> 1/1000 짜리 꼬리가 전체 소요를 12배로 만들었고, 그 숫자를 그대로
> 믿었으면 틀린 결론을 문서에 박을 뻔했다.

### D-2. 매체 API 타임아웃 ✅ 실측

**실패를 만드는 게 첫 관문이었다.** GA4 는 일부러 깨진 페이로드를 보내도
2xx 를 돌려준다(→ [outbox-and-channels](outbox-and-channels.md)). 매체가 우리
사정에 맞춰 4xx·5xx 를 내주지 않으니, 실패 경로를 한 번도 끝까지 가 보지
못한 채로 "지표 100%" 를 보고 있었던 것이다.

`NoopChannel` 이 이미 `outcome` 인자를 받고 있었는데 `Channels` 에서 넘기지
않고 있었다. `.env` 의 `NOOP_OUTCOME` 으로 노출했다.

```bash
NOOP_OUTCOME=sent    # 204  기본값
NOOP_OUTCOME=retry   # 503  5xx — 재시도 대상
NOOP_OUTCOME=dead    # 400  4xx — 재시도하지 않는다
```

| 시나리오 | 예상 | 결과 | |
|---|---|---|---|
| 첫 시도 타임아웃 | `pending` + `next_retry_at` | **`pending`, 33.5초 뒤**, `http_status` **NULL** | ✅ |
| 재시도 5회 모두 실패 | `dead` | **attempt 6 에서 `dead`** | ✅ |
| 3회째 성공 | `sent` | **attempt 3 에서 `sent`**, `last_error` NULL 로 지워짐 | ✅ |
| 매체가 5xx | 재시도 | **503 × 5회 재시도** | ✅ |
| 매체가 4xx | **재시도 안 함** | **attempt 1 에서 즉시 `dead`** | ✅ |

#### ① 5xx — 사다리를 끝까지 걸어갔다

```
[1] #13835 noop attempt=1 → failed (http=503)
[2] #13835 noop attempt=2 → failed (http=503)
[3] #13835 noop attempt=3 → failed (http=503)
[4] #13835 noop attempt=4 → failed (http=503)
[5] #13835 noop attempt=5 → failed (http=503)
[6] #13835 noop attempt=6 → dead   (http=503)
```

`BackoffPolicy::WAIT_SECONDS` 에 1~5 만 있으므로 `attemptsMade=6` 에서
`nextRetryAt` 이 `null` 을 돌려주고, 모델이 그걸 `dead` 로 옮긴다.
**포기 지점이 별도 카운터가 아니라 사다리의 끝이라는 것**이 여기서 보인다.

> **백오프 대기는 기다리지 않고 `next_retry_at` 을 `NOW(3)` 으로 당겼다.**
> 사다리 전체를 실시간으로 기다리면 30s+2m+10m+1h+3h ≈ 4시간이다.
> 그래서 이 실험이 검증한 것은 **상태 기계와 시도 사다리**지 대기 길이가
> 아니다. 대기 길이와 지터는 [benchmarks 4-0](benchmarks.md)에서 따로 쟀다.

#### ② 4xx — 한 번에 포기했다

```
[1] #13836 noop attempt=1 → dead (http=400) · noop: 포기 흉내
```

`shouldRetry(400)` 이 `false` 라 `next_retry_at` 을 받지 못하고 바로 `dead` 다.
**이게 없으면 잘못된 페이로드를 다섯 번 더 보낸다.** 매체 쪽에서 보면
같은 잘못된 요청이 4시간에 걸쳐 여섯 번 오는 것이고, 고쳐야 할 것은
타이밍이 아니라 요청이다.

#### ③ 타임아웃 — `http_status` 가 NULL 이라는 것이 신호다

`DISPATCH_TIMEOUT_MS=1` 로 GA4 를 불렀다.

```
#13837 ga4 attempt=1 → failed (http=-, 9ms) · Resolving timed out after 4 milliseconds
```

| | |
|---|---|
| `http_status` | **NULL** |
| `status` | `pending` |
| `next_retry_at` | **33.5초 뒤** (기본 30초 + 지터 ±20%) |

`shouldRetry(null)` 이 `true` 인 이유가 여기 있다 — **응답이 없다는 것과
응답이 4xx 라는 것은 다르다.** 전자는 일시적일 수 있고 후자는 아니다.

> **한계 하나.** 에러 원문이 `Resolving timed out` 이다. 1ms 는 DNS 해석보다
> 짧아서 **연결도 못 해 보고 끊긴 것**이다. 실제로 워커를 붙잡는 실패는
> 이쪽이 아니라 **연결은 됐는데 응답이 안 오는** 경우인데, 그건 아직 못 쟀다.
> 재려면 느리게 응답하는 서버를 세워야 한다.

#### 곁가지 — 매체를 빼면 그 큐는 어떻게 되는가

`CHANNELS` 를 `ga4` 에서 `noop` 으로 바꾼 뒤 남아 있던 ga4 행이 이렇게 나왔다.

```
#13834 ga4 → dead (어댑터 없음)
```

의도한 동작이다. 어댑터가 없으면 재시도해도 생기지 않으므로 `pending` 으로
두면 워커가 영원히 같은 행을 집었다 놓는다 → `cli/Dispatch::handle`

#### 아직 아닌 것

- **알림이 없다.** 원래 표에 "`dead` 처리, 알림" 이라고 적어 뒀는데 `dead` 까지만
  구현돼 있다. 지금은 `cli/dispatch status` 로 봐야 안다
- `last_error` 는 성공하면 `NULL` 로 지워진다. 실패 이력은 행이 아니라
  `dispatch_log` 에 남는다 — 행만 보고 "문제없이 갔다" 로 읽으면 안 된다

## E. 데이터 정합성

### E-1. 복제 지연 (read-after-write) ✅ 실측

복제본에 지연을 걸었다. `.env` 의 `REPL_DELAY_SECONDS` 는 **컨테이너 첫 기동에만**
적용되므로(`docker-entrypoint-initdb.d`), 볼륨이 이미 있는 서버에서는 직접 건다.

```sql
STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 10;
START REPLICA;
```

랜딩 화면(`/l/{work}`)은 수집 이벤트를 **배정받은 복제본에서** 읽는다.
이 프로젝트에서 복제본을 읽는 경로는 여기 하나뿐이고, 일부러 그렇게 뒀다 —
`MY_Controller::read()` 의 규칙("직전에 내가 쓴 것을 읽는가")을 **의도적으로
어긴 자리**라서 지연이 눈에 보인다.

`/collect` 로 `click` 을 하나 쓴 직후, **같은 방문 · 같은 순간에 읽기 대상만** 바꿨다.

| 시점 | `rdb1` (프라이머리) | `rdb2` (복제본) |
|---|---|---|
| 쓰기 전 | 0개 | 0개 |
| **쓴 직후** | **1개** | **0개** |
| 12초 뒤 | 1개 | **1개** |

```
POST /collect → 200
  프라이머리 1 건 · 복제본 0 건

ab_rdb=rdb1  → read_target=rdb1   click 행 1개
ab_rdb=rdb2  → read_target=rdb2   click 행 0개     ← 같은 URL, 같은 순간
```

**같은 URL 이 같은 순간에 다른 답을 준다.** 사용자에게는 "방금 한 게 사라졌다"
로 보이고, 새로고침하면 (다른 복제본에 배정되면) 다시 나타난다. 재현이 안 되는
버그의 전형적인 모양이다.

복제본이 따라잡는 과정도 그대로 보인다.

```
+1초  아직 0건 · Seconds_Behind_Source=1
+3초  아직 0건 · Seconds_Behind_Source=4
+5초  아직 0건 · Seconds_Behind_Source=7
+9초  아직 0건 · Seconds_Behind_Source=12
+10초 도착 (1 건)
```

`SQL_Delay=10` 을 정확히 지켰다. `Seconds_Behind_Source` 가 10을 넘어 12까지
올라간 것은 **이 값이 "지연 설정" 이 아니라 "가장 오래된 미적용 이벤트의 나이"**
이기 때문이다 — 의도한 지연과 밀린 정도가 같은 숫자에 섞여 있다.
모니터링에서 이 값 하나로 경보를 걸면 `SOURCE_DELAY` 를 쓰는 순간 상시 경보가 된다.

#### 배정 쿠키를 먼저 만났다

처음엔 같은 쿠키 항아리로 8번 불러 놓고 **8번 다 `rdb1`** 이 나왔다.
09-09에 겪은 배정 쏠림 버그가 돌아온 줄 알았는데, 아니었다.

```lua
local COOKIE_NAME = "ab_rdb"   -- 있으면 고정한다. Set-Cookie 를 다시 내리지 않는다
```

**의도한 동작이다.** 플랫폼 A 가 `…slave=sdb3` 쿠키로 세션을 복제본에 고정하는
것을 재현한 부분이고(→ [ADR-007](decisions/ADR-007-read-write-split.md)),
한 사용자가 요청마다 다른 신선도를 보는 일을 막는다.

> 다만 **고정은 완화지 해결이 아니다.** 고정해도 그 사용자가 붙은 복제본이
> 늦으면 자기가 쓴 것을 못 본다. 해결은 "쓴 직후 읽기는 프라이머리로" 뿐이고,
> 그게 `read()` 의 주석에 적힌 판단 기준이다.

### E-2. 보존기간 파기 ✅ 실측

**먼저 파기 배치가 없다는 것을 발견했다.** `data-model.md` 7장에 보존기간 표와
`DELETE` 두 줄이 적혀 있었지만, 그걸 도는 코드가 없었다.
**파기되지 않는 보존정책은 정책이 아니라 문장이다.** `cli/purge` 를 만들었다.

100일 전에 광고를 타고 들어와 가입한 회원 하나를 고정물로 넣었다.

| | 파기 전 | 파기 후 |
|---|---|---|
| `visits` | 1 | **0** |
| `touchpoints` | 2 | **0** |
| `users` | 1 | **1** |

```
cli/purge plan
  기준 시각 2026-06-14 20:29:38 (보존 90일) — 세기만 합니다
    touchpoints    2 건
    visits         1 건

cli/purge run
    touchpoints    2 건 삭제 · 7ms
    visits         1 건 삭제 · 6ms
```

**같은 질문을 두 경로로 물었다 — "이 회원은 어느 캠페인으로 들어왔나".**

| | 파기 전 | 파기 후 |
|---|---|---|
| `users.signup_pid` (스냅샷) | `e2camp` | **`e2camp`** |
| `touchpoints` 조인 | `e2camp` | **NULL** |

```
+----+------------+-----------------+-------------------+
| id | signup_pid | signup_visit_id | 조인해서 얻은 pid |
+----+------------+-----------------+-------------------+
|  1 | e2camp     |             585 | NULL              |   ← 파기 후
```

> **이게 스냅샷 비정규화가 정당한 이유다.** 방문기록은 3개월(통신비밀보호법),
> 회원은 5년(전자상거래법). 20배 차이 나는 것을 같은 테이블에 두면
> 파기가 불가능해진다. 정규화를 깬 이유가 성능이 아니라 **법**인 경우다.

`signup_visit_id = 585` 는 이제 **없는 행을 가리킨다.** FK 를 걸지 않은 것이
설계다 — 걸었다면 파기가 `ON DELETE` 규칙에 붙잡힌다.

| FK 를 걸었다면 | 결과 |
|---|---|
| `RESTRICT` | **파기 자체가 막힌다.** 법정 보존기간을 못 지킨다 |
| `CASCADE` | 방문이 사라질 때 **회원까지 지워진다** |
| `SET NULL` | 스냅샷의 연결이 끊긴다. 값은 남지만 어느 방문이었는지 영영 모른다 |

셋 다 틀렸다. 그래서 컬럼 주석이 `"FK 없음 — visits 는 3개월 뒤 사라진다"` 다.
**참조 무결성을 일부러 포기한 자리이고, 그 이유가 스키마에 적혀 있어야 한다.**

#### 파기 배치를 끊어서 도는 이유

```php
do { DELETE … LIMIT $chunk; } while ($n === $chunk);
```

통째로 지우면 큰 트랜잭션이 되고, **복제본이 그걸 단일 스레드로 다시 적용하느라
읽기 지연을 만든다.** [6장 리소스](benchmarks.md)에서 복제본이 프라이머리와 같은
CPU 를 쓰는 것을 재면서 확인한 성질이다. 파기 배치가 E-1 을 일으키는 것은 본말전도다.

#### 아직 아닌 것

- **스케줄러가 없다.** `cli/purge` 는 손으로 돈다. cron 은 인스턴스에 이미 있으므로
  한 줄이면 되지만, 무인 삭제를 붙이기 전에 `plan` 을 며칠 지켜보는 편이 낫다
- 5년 쪽(회원 탈퇴·법정 보존기간 만료) 파기는 규칙이 달라 넣지 않았다

## 요약표 (완성 시 README로 발췌)

| # | 시나리오 | 무엇이 깨지는가 | 어떻게 막았는가 |
|---|---|---|---|
| B-2 | `Allow-Origin: *` + credentials | 브라우저가 응답을 차단. **그런데 서버는 기록한다** → 재시도가 붙으면 전환이 부풀려짐 | 오리진을 정확히 반향 + `Vary: Origin`. 정책을 `src/Http/CorsPolicy` 로 빼고 테스트 16건으로 못박음 |
| B-3 | `sendBeacon` 헤더 불가 | 헤더를 못 붙이고 **성공 여부도 알 수 없다**. 대신 CORS 오설정에도 통과 | 두 경로를 모두 구현해 `transport` 로 구분 적재. 확인은 서버 큐가 담당 |
| C-1 | 캐시 헤더 없는 301 | 두 번째 클릭부터 요청이 **서버에 오지 않는다**. 3회 로드 → 1회 도달. 더 나쁜 것은 **302 로 고쳐도 이미 캐시한 브라우저는 안 돌아온다** (같은 URL 2회 로드 → 0회 도달) | 302 고정 + `no-store`. 301 은 `.env` 스위치로만 재현. PHP `session.cache_limiter` 가 이미 같은 헤더를 붙이고 있었다는 것도 이때 알았다 |
| C-2 | 랜딩 URL 공유 | **A(passthru)**: 클릭 1회가 유입 2건으로 부풀었다(방문 2개). **B(vid)**: 건수는 그대로지만 링크를 받은 사람이 원래 방문자의 쿠키를 물려받아 **두 사람이 한 방문**이 됐다 | 기본값을 B 로. 정산이 걸린 것은 건수 쪽이고, vid 에는 권한·개인정보가 붙어 있지 않아 주워도 할 수 있는 일이 없다 |
| C-3 | 오픈 리다이렉트 | 위험한 입력은 `?return=`(애초에 없다)이 아니라 **`Host` 헤더**였다 — 브리지가 Location 을 `$http_host` 로 만든다. 막혀 있긴 했지만 **443 서버 블록 순서에 기댄 우연**이었다 | 목적지를 입력으로 받지 않는다. `work` 는 1~18자리 숫자만(헤더 분할·경로 조작 전부 400). 엣지 443 에 `default_server` 명시, `api.` 는 `requireHost` 가 404 |
| D-1 | 워커 중복 실행 | 중복은 네 조건 모두 **0**. 다만 **`SKIP LOCKED` 를 꺼도 처리량이 안 떨어졌다**(오히려 조금 빨랐다) — 잠금 구간에 외부 I/O 가 없어 대기가 마이크로초라서다 | 선점과 상태 변경을 한 트랜잭션에, HTTP 는 트랜잭션 밖에. `SKIP LOCKED` 는 처리량이 아니라 보험으로 남긴다 |
| D-2 | 매체 장애 | 5xx·타임아웃은 **사다리 끝(attempt 6)에서 `dead`**, 4xx 는 **attempt 1 에서 즉시 `dead`**, 3회째 복구되면 `sent`. 타임아웃은 `http_status` 가 **NULL** 로 구분된다 | `BackoffPolicy::shouldRetry` 가 4xx/5xx/무응답을 가른다. 실패 주입은 `NOOP_OUTCOME` 스위치 — GA4 는 깨진 페이로드에도 2xx 를 준다 |
| E-1 | 복제 지연 | **같은 URL 이 같은 순간에 다른 답**을 준다 — 쓴 직후 `rdb1` 1개 / `rdb2` 0개, 10초 뒤 일치. 재현 안 되는 버그의 전형 | 쓴 직후 읽기는 프라이머리(`$this->db`). 배정 쿠키 고정은 **완화지 해결이 아니다** |
| E-2 | 보존기간 파기 | 방문·접점은 사라지고 **회원 스냅샷은 남는다**. 같은 질문에 조인은 `NULL`, `signup_pid` 는 `e2camp` | 스냅샷 비정규화 + `signup_visit_id` 에 **FK 없음**. FK 셋(RESTRICT/CASCADE/SET NULL) 다 틀린 자리 |

## 하지 않기로 한 것 — A-1 · A-2

**등록 도메인을 1개로 정하면서 두 시나리오를 범위에서 뺐다** → [ADR-018](decisions/ADR-018-single-registered-domain.md)

| # | 시나리오 | 왜 못 하는가 |
|---|---|---|
| A-1 | 서드파티 쿠키 차단 (브라우저별 매트릭스) | 브라우저는 same-site를 **eTLD+1**로 판정한다. `lp.sshwan.com` → `api.sshwan.com`은 같은 사이트라 차단이 애초에 발동하지 않는다 |
| A-2 | `SameSite=None` 누락 | same-site 요청에는 `Lax`로 충분하다. `None`이 필요한 상황 자체가 만들어지지 않는다 |

### 남은 것은 무엇인가

수집 호스트를 `api.sshwan.com`에 두면 `lp.` → `api.` 는

- **same-site** (등록 도메인 동일) → 서드파티 쿠키 차단 없음
- **cross-origin** (서브도메인 상이) → **CORS는 그대로 적용**

그래서 **B-2와 B-3은 계속 재현된다.** preflight도, `Vary: Origin`도, `Allow-Origin: *`와 `credentials: include`의 충돌도 오리진 기준이지 사이트 기준이 아니기 때문이다.

> **이 구분을 정확히 아는 것 자체가 이 항목의 산출물이다.**
> "크로스사이트가 아니면 CORS도 없다"는 흔한 오해이고, 처음에는 나도 그렇게 묶어서 **잃는 시나리오를 4개로 과대평가했다.** 실제로는 2개다.

### 되돌리는 조건

추적 도메인이 생기면 `.env`의 `TRACK_DOMAIN` 한 줄 + DNS A 레코드 + certbot 재발급으로 붙는다. 엣지는 `TRACK_DOMAIN`이 비어 있어도 뜨도록 만들어 뒀고 CI가 두 경우를 모두 검사한다. **코드는 준비돼 있고 도메인만 없다.**
