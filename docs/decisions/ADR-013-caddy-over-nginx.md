# ADR-013 · 리버스 프록시로 Nginx가 아니라 Caddy

**상태**: 확정 (2026-09-08)

## 배경

서비스&인프라 포지션([ADR-012](ADR-012-observability-scope.md) 참조)의 우대사항에 **"Nginx, Apache 등 웹 서버를 사용하거나 직접 설정해 본 경험"** 이 있다. 그쪽에 맞추려면 Nginx가 자연스러워 보인다.

또한 대상 서비스의 응답 헤더에서 **OpenResty(Nginx + Lua)** 가 관측됐다 → [조사 요약](../research-method.md). 조직 표준은 Nginx 계열이다.

## 결정

**Caddy 2를 쓴다.** 다만 그 이유와 Nginx로 갈 경우의 차이를 문서로 남긴다.

## 근거

이 프로젝트는 **등록 도메인 2개에 걸쳐 호스트 3개의 인증서**가 필요하고, `SameSite=None; Secure` 쿠키가 전제라 **HTTPS 없이는 실험 자체가 성립하지 않는다**([ADR-002](ADR-002-two-registered-domains.md)).

| | Caddy | Nginx |
|---|---|---|
| ACME 자동 발급·갱신 | **내장.** 설정 3줄 | certbot 별도 구성 + 갱신 크론 + 재적재 훅 |
| 두 도메인 다중 호스트 | 사이트 블록 3개 | 동일하나 인증서 배선이 수동 |
| 13일 일정에서의 위험 | 낮음 | **초반 이틀을 인증서 배선에 쓸 위험** |

**M1(인프라)에 배정된 시간이 이틀**이다. 그 안에 도메인 구입·DNS 전파·EC2·swap·Docker·TLS를 다 끝내야 한다. 여기서 certbot 배선에 막히면 뒤가 통째로 밀린다. **Caddy는 일정 리스크를 줄이는 선택이다.**

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **Nginx + certbot** | 위 표. 얻는 것은 "Nginx를 써봤다"인데, 그건 이 프로젝트가 증명하려는 것이 아니다 |
| Nginx와 Caddy 병행 | 컨테이너 추가 + 설정 두 벌. t3.micro에 낭비 |
| OpenResty(대상 조직과 동일) | Lua 계층까지 흉내 낼 이유가 없다. **맞추는 것과 베끼는 것은 다르다** |

## 결과

- **감수**: Nginx 설정 경험을 이 저장소로 증명하지 못한다
- **완화**: 두 서버의 차이(ACME 처리, 설정 문법, 기본 보안 헤더)를 **알고 선택했다는 것**이 이 문서로 남는다. 면접에서 "Nginx는 안 써보셨나요"에 대한 답이 준비된다

> "조직 표준이 Nginx 계열인 건 응답 헤더로 확인했습니다. 다만 이 프로젝트는 도메인 두 개에 걸친 자동 HTTPS가 전제라, 인증서 배선에 이틀을 쓰지 않으려고 Caddy를 택했습니다. 같은 구성을 Nginx로 하면 certbot과 갱신 훅이 추가로 필요합니다."

- **전환점**: 인증서를 외부(로드밸런서·CDN)에서 종단하는 구조가 되면 Caddy의 이점이 사라진다. 그때는 Nginx가 낫다
