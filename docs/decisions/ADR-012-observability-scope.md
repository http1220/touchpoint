# ADR-012 · 관측 가능성을 어디까지 넣을 것인가

**상태**: 확정 (2026-09-08) — 지원 포지션 2곳 대응으로 **추가된 항목**

## 배경

같은 회사 개발실에 웹개발자 공고가 **세 개** 있고 전부 같은 날 마감이며 복수 지원이 가능하다.

| # | 공고 | 업무 핵심 |
|---|---|---|
| **1** | 플랫폼 개발 및 **광고 매체 연동** | 매체 연동 추적 · **도메인·Redirect 유입 환경에서의 전환 추적** |
| 2 | 콘텐츠 플랫폼 | PHP 레거시 개선 · 대규모 트래픽 |
| **3** | **서비스&인프라 운영** | **Linux 서버 구축·운영 · 모니터링 및 장애 원인 분석·대응** · 성능 개선 |

이 프로젝트는 #1에 맞춰 설계됐다. #3에도 지원하기로 했으므로, **#1을 흐리지 않으면서 #3의 핵심 문장(모니터링·장애 분석)에 실물로 답할 수 있는 최소한**을 정한다.

## 결정

**어트리뷰션 범위는 건드리지 않는다.** 대신 이미 계획에 있던 계측을 **운영 관점의 관측 가능성으로 승격**시킨다. 새 기능을 더하는 게 아니라, 있는 것을 밖에서 볼 수 있게 만드는 일이다.

| 추가 | 내용 | 비용 |
|---|---|---|
| **구조화 로그 + `trace_id`** | JSON 로그, 요청부터 매체 전송까지 상관 ID 전파 | M2에 녹임 (0.5일 미만) |
| **`/health`** | DB 연결 · 아웃박스 적체 · 복제 지연 · 워커 최종 처리 시각 | 0.5일 |
| **`/metrics`** | Prometheus exposition 형식으로 노출 | 위와 함께 |
| **관측 프로파일** | `--profile obs` 로 Prometheus + Grafana를 **필요할 때만** 기동 | 0.5일 |
| **탐지 경로 기록** | `failure-scenarios.md` 각 시나리오에 **"무엇을 보고 알아챘는가"** 열 추가 | 0 (표 열 하나) |

### 대신 버리는 것

**자체 지표 화면(`/metrics` Chart.js 대시보드)을 만들지 않는다.** 컷 순서 1순위였던 항목이다.

Grafana가 그 역할을 대신한다. 결과적으로 **시간은 늘지 않거나 오히려 줄고**, #1(계측)과 #3(모니터링) 양쪽에 동시에 답한다. 직접 만든 차트보다 표준 도구를 붙인 쪽이 운영 관점에서 더 설득력 있다는 판단도 있다.

## 근거

**#3의 업무 문장이 "모니터링 및 장애 원인 분석·대응"이다.** 문서로 "장애를 재현했습니다"라고 쓰는 것과, **무엇을 보고 알아챘는지**를 보여주는 것은 다르다. 후자가 운영이다.

그리고 이 추가분은 **#1에도 손해가 아니다.** 매체 전송 성공률·구간별 소요 시간은 원래 계측 항목이었고([benchmarks.md](../benchmarks.md)), 그걸 Grafana로 보는 것뿐이다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **Kubernetes 도입** | #3 우대사항에 있지만 13일에 불가능하고 [ADR-010](ADR-010-no-kubernetes.md)을 뒤집어야 한다. 컨테이너 4개짜리에 K8s를 얹으면 **판단력이 없어 보이는 쪽**이 위험이 크다 |
| **Prometheus·Grafana 상시 기동** | t3.small RAM 2GB에 이미 MySQL 2대가 있다. 컨테이너 2개 추가는 OOM 위험. **프로파일로 분리해 계측할 때만** 띄운다 |
| Caddy를 Nginx로 교체 | #3 우대사항에 Nginx가 있으나, 두 도메인 자동 HTTPS(ACME)가 이 프로젝트의 전제다. → [ADR-013](ADR-013-caddy-over-nginx.md) |
| **프로젝트를 #3 중심으로 전환** | 기존 경력(성능·장애 분석)과는 더 맞지만, 13일에 방향 전환은 불가능하고 **어트리뷰션의 희소성을 잃는다.** 주니어 인프라 지원자는 대개 비슷한 홈랩을 들고 온다 |
| 아무것도 안 함 (#1만) | #3 지원서에서 프로젝트가 "관련은 있는데 증거는 없는" 상태가 된다 |

## 결과

- **일정**: 순증 약 0.5일. 자체 대시보드를 버려서 상쇄된다
- **한계 명시**: Prometheus·Grafana는 상시 운영이 아니라 **계측 시 기동**이다. 스크린샷과 재현 절차로 남기고, 실물 상시 운영인 척하지 않는다
- **지원서 분리**: 같은 저장소를 쓰되 README 강조 문단과 지원서를 포지션별로 다르게 쓴다. 두 지원서가 동일하면 역효과다

## 두 포지션을 잇는 축

면접에서 "왜 이 포지션인가"는 양쪽 모두에서 나온다. 방향이 아직 정해지지 않았다면 **공통 축**을 잡아 두 지원서에 일관되게 쓴다.

> **"안 보이는 것을 숫자로 만드는 일을 해왔습니다."**
> 어트리뷰션은 **유입이 어디서 새는지**를 재는 일이고,
> 모니터링은 **시스템이 어디서 느려지는지**를 재는 일이다.
> 둘 다 측정이고, 기존 경력(응답을 7단계로 쪼개 병목 특정, 인식률 68%→92.6%)도 측정이다.

이 축이 있으면 "아무 데나 지원했다"가 아니라 "같은 관심사의 두 갈래"가 된다.
