# ADR-002 · 등록 도메인 2개로 분리

**상태**: 확정 (2026-09-07) — **이 프로젝트에서 가장 중요한 결정**

## 배경

초기 설계안은 서브도메인 3개(`lp.` / `api.` / `app.example.com`)를 "일부러 다른 오리진으로 갈라놓는다"고 했다. 목적은 CORS와 `SameSite`, 서드파티 쿠키 차단을 모두 겪는 것이었다.

## 문제

**브라우저의 same-site 판정 기준은 오리진이 아니라 등록 도메인(eTLD+1)이다.** 셋 다 `example.com`이면 same-site다.

| 겪겠다고 한 것 | 서브도메인 3개로 실제 벌어지는 일 |
|---|---|
| CORS preflight | 발생 (cross-origin은 맞음) |
| `SameSite=None; Secure` 필요 | **불필요.** `Lax`로도 쿠키가 전송됨 |
| 서드파티 쿠키 차단 재현 | **불가능.** 전부 first-party |
| "SameSite 3종 차이" 면접 답변 | **겪은 게 없어 책 내용밖에 말할 게 없음** |

→ 광고 어트리뷰션의 **핵심 난제를 하나도 못 겪은 채 끝난다.**

## 결정

**등록 도메인 2개**를 산다. 현실의 광고 추적처럼 **광고주 도메인 ≠ 추적 도메인**으로 가른다.

```
sshwan.com    lp.  (랜딩·브리지)   app. (서비스·전환·지표)
khan-edge.com    api. (수집 API)
```

| 호출 | 관계 | 역할 |
|---|---|---|
| `lp.sshwan.com` → `api.khan-edge.com` | **cross-site** | 실험군 |
| `lp.sshwan.com` → `app.sshwan.com` | same-site, cross-origin | **대조군** |

## 근거

**대조군이 있어야 증명이 된다.** "cross-site면 막히고 same-site면 통과한다"를 나란히 보여줘야, 원인이 오리진이 아니라 사이트라는 것이 드러난다. 한쪽만 있으면 관찰이지 실험이 아니다.

## 두 번째 도메인이 정확히 무엇을 사는가

**공고 스킬 태그는 도메인 1개로도 전부 커버된다.** 이걸 먼저 인정하고 시작해야 한다.

| 태그 | 서브도메인만으로 되는가 |
|---|---|
| `CORS` | **된다.** 서브도메인은 cross-**origin**이므로 preflight가 실제로 발생한다 |
| `Cookie` `Domain` | 된다. `Domain=.example.com`, `Lax`, `Secure`, `HttpOnly` 전부 |
| `Redirect` | 된다 |
| 나머지 전부 | 도메인 수와 무관 |

두 번째 도메인이 사는 것은 **딱 하나**다.

> `SameSite=None` · **서드파티 쿠키 차단** · **브라우저별 차단 매트릭스**

즉 이건 *태그 요건*이 아니라 **차별화 콘텐츠**다. 공고에 "서드파티 쿠키"라는 말은 없다.
그러니 "필수라서 산다"가 아니라 **"이게 이 포트폴리오에서 남들이 안 가진 유일한 부분이라 산다"**가 정확한 이유다.

## 기각한 대안

| 대안 | cross-site | 공고 태그 | 기각 사유 |
|---|---|---|---|
| 서브도메인 3개 (도메인 1개) | ❌ | ✅ | 위 문제. **다만 태그는 다 커버된다** — 차별화를 포기하는 선택 |
| 도메인 1개 + 다른 포트 | ❌ | ✅ | 포트는 same-site 판정에 영향을 주지 않는다 |
| **도메인 1개 + DuckDNS** | **✅** | ✅ | `duckdns.org`는 **공개 접미사 목록(PSL)에 등재**돼 있어 그 아래가 별도 등록 도메인이 된다. A 레코드를 우리 EC2로 돌릴 수 있어 **기술적으로 성립한다.** 기각 사유는 아래 |
| 도메인 1개 + `workers.dev`·`netlify.app` 등 | ✅ | ✅ | PSL에는 있지만 **자체 호스팅이라 우리 앱을 못 올린다.** 프록시를 끼우면 쿠키 동작에 층이 하나 더 생겨 관측이 흐려진다 |
| 도메인 1개 + `nip.io`·`sslip.io` | ❌ | ✅ | **PSL에 없다.** 모든 `nip.io` 호스트가 한 사이트로 묶여 same-site가 된다 |
| 로컬 `.test` 2개 | ✅(로컬) | ✅ | 비용 0에 cross-site도 성립하지만 **공개 URL이 없고**, 브라우저마다 로컬 CA를 신뢰시켜야 하며, **Safari ITP가 `.test`에 같게 동작하는지 자체가 미검증 전제**가 된다 |

### DuckDNS를 기각한 이유

기술적으로는 된다. 그런데 **동적 DNS 제공자는 악성 인프라에 흔히 쓰여 위협 인텔리전스 차단 목록에 자주 오른다** [추정 — 확인 절차는 아래].

그러면 [domain-setup.md](../domain-setup.md) 2장에서 저가 TLD를 배제한 것과 **같은 문제**가 생긴다.

> 요청이 막혔을 때 `SameSite` 때문인지 도메인 평판 때문인지 구분할 수 없다.

두 번째 도메인을 사는 유일한 이유가 **깨끗한 측정**인데, 그 측정을 오염시킬 수 있는 수단으로 아끼는 것은 앞뒤가 맞지 않는다.

**확인 절차**: 결제 전에 광고 차단기를 켜고 `<후보>.duckdns.org` 접속을 시도해 차단기가 반응하는지 본다. 반응하지 않는다면 DuckDNS도 유효한 선택지다 — 이 판단은 관측으로 뒤집힐 수 있다.

## 비용

| 항목 | 2번째 도메인의 한계 비용 |
|---|---|
| 등록 | `.com` 연 $15 내외 |
| 호스팅 영역 | 월 $0.50 = 연 $6 |
| 시간 | DNS 레코드 1개 추가(10분) + ICANN 인증 메일 1건 |
| **합계** | **연 약 3만원 · 작업 15분** |

이 프로젝트에서 가장 값싼 지출이다. 반대로 아껴서 얻는 것은 3만원이고, 잃는 것은 **남들이 안 가진 유일한 부분**이다.

## 결정을 뒤집는다면

도메인을 1개로 간다면 **주장도 함께 내린다.** README와 `failure-scenarios.md`에서 서드파티 쿠키·브라우저 매트릭스 항목을 지우고, `SameSite`는 문서상 설명으로만 남긴다.
**증거 없는 주장을 남겨두는 것이 도메인을 아끼는 것보다 훨씬 큰 손해다.**

## 결과

- **비용**: 도메인 1개 값 추가 (연 1~2만원). 이 프로젝트에서 가장 값싼 지출
- **운영**: OpenResty 한 대가 두 도메인 인증서를 각각 ACME(certbot webroot)로 발급. DNS A 레코드는 같은 EIP로
- **위험**: ACME rate limit. 설정 시행착오는 **staging 엔드포인트로 먼저** 검증한다
