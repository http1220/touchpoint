# ADR-014 · 스택을 대상 조직에 정렬한다

**상태**: 확정 (2026-09-08) — **다른 모든 ADR을 지배하는 원칙**

## 배경

이 프로젝트의 목적을 다시 놓고 보면 이렇다.

> **대상 조직에서 요구하는 경험을 만든다.** 그 회사 스택으로, 그 도메인에서 반드시 터지는 문제를 실제로 겪는다.

그런데 ADR-001~013은 다른 목적함수로 결정돼 있었다.

| ADR | 실제 판단 근거 | 문제 |
|---|---|---|
| 001 CodeIgniter **4** | "현행 버전" | 대상은 **CI 2.x**. CI4는 완전 재작성이라 관용구가 다르다 |
| 013 **Caddy** | "M1이 이틀이라 certbot 배선 위험" | **일정 편의**. 대상은 OpenResty |
| 007 커넥션 분리 **흉내** | "t3.micro RAM 1GB" | **비용 편의**. 대상은 복제본 5대 실물 |

전부 **일정 안전과 현대적 모범사례**를 최적화한 결정이다. 목적은 그게 아니었다.

## 결정

**"가능한 한 그대로"를 지배 원칙으로 삼는다.** 스택 선택의 기준을 바꾼다.

| 이전 기준 | 새 기준 |
|---|---|
| 이 선택이 더 나은가? | **이 경험이 그 회사 업무에서 그대로 쓰이는가?** |
| 일정 안에 안전한가? | 안전을 이유로 목적을 포기하고 있지 않은가? |

## 정렬표

| 계층 | 대상 조직 | 이 프로젝트 | 판정 |
|---|---|---|---|
| 앱 프레임워크 | CodeIgniter 2.x | **CodeIgniter 3** | 타협 — [ADR-001](ADR-001-php-codeigniter.md) |
| 프론트 | jQuery + 서버 렌더 | **jQuery + 서버 렌더** | **그대로** |
| 웹서버 | OpenResty (Nginx+Lua) | **OpenResty** | **그대로** — [ADR-013](ADR-013-caddy-over-nginx.md) 뒤집음 |
| 복제본 배정 | `slave` 쿠키 | **Lua로 동일 구현** | **그대로** |
| DB | MySQL + 복제본 5대 | **MySQL primary + replica 실물** | 축소하되 **실물** |
| 모바일 분기 | UA 스니핑 → 302 → `m.` | **동일 재현** | **그대로** |
| 추적 분류 | `pid`/`subpid`/`channel` × 언어 | 동일 | **그대로** |
| 이미지 | S3 + CDN | 생략 | **포기** |
| 결제 | PG 약 30곳 | 스텁 1개 | **불가** |
| 광고 매체 | 10종 이상 | GA4 + Meta + 어댑터 | 축소 |

## 세 가지 판정 기준

정렬이 항상 옳은 건 아니다. 세 갈래로 나눈다.

**① 그대로 간다** — 재현 비용이 감당 가능하고, 그 경험이 업무에 직결될 때
OpenResty, Lua 복제본 배정, UA 302 분기, jQuery 서버 렌더, 추적 분류 체계.

**② 타협한다** — 그대로 가면 안 되는 이유가 있을 때. **그 이유를 문서로 남긴다**
CodeIgniter 2 → 3. CI2는 PHP 8을 지원하지 않고 보안 패치가 11년째 없다. **공개 서버에 올릴 수 없다.**
CI3는 CI2와 관용구가 거의 같고(`$this->load->model()`, URI 라우팅, 헬퍼), 공식 마이그레이션 경로도 **CI2 → CI3 → CI4**다. 즉 CI3는 **그들의 다음 단계**다.

**③ 포기한다** — 재현 비용이 목적 대비 과할 때. **포기했음을 밝힌다**
이미지 파이프라인(S3+CDN), PG 30곳, 매체 10종.

> **흉내를 실물로 포장하지 않는다**는 기존 원칙은 그대로다. 다만 이제 **흉내를 실물로 바꿀 수 있으면 바꾼다.**

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **CodeIgniter 2를 그대로 사용** | PHP 8 미지원, 보안 패치 11년 부재. **인터넷에 노출된 서버에 올리는 것은 무책임하다.** 정렬이 안전을 이길 수는 없다 |
| 현재 설계 유지 (CI4·Caddy·단일 DB) | 일정은 안전하나 **"그 회사 스택으로 일해봤다"는 주장을 할 수 없다.** 이 프로젝트의 존재 이유가 사라진다 |
| 스택은 그대로 두고 문서로만 정렬 | 겪지 않은 것을 안다고 쓰는 것이다. 면접에서 한 겹만 파면 드러난다 |
| 전부 정렬 (이미지·PG·매체까지) | 13일에 불가능. **선택적 정렬이 정렬 포기보다 낫다** |

## 결과

- **일정 순증 약 2.7일.** Meta CAPI · 인덱스 EXPLAIN 실측 · Prometheus·Grafana를 잘라 상쇄한다
- **인스턴스 t3.micro → t3.small.** MySQL 2대 + OpenResty + PHP-FPM에 1GB는 불가. 2주 약 $15
- **Prometheus·Grafana 대신 Lua 복제본 배정이 인프라 포지션 대응을 맡는다**([ADR-012](ADR-012-observability-scope.md) 수정). 대시보드를 붙이는 것보다 **그들이 실제로 하는 일을 구현하는 쪽**이 강하다
- **얻는 것**: "OpenResty에서 Lua로 읽기 복제본을 배정하고, CI3 위에서 유입 추적을 붙여봤습니다"가 사실이 된다

## 이 원칙이 만드는 면접 카드

> "쿠키에 복제본 번호가 붙는 걸 보고 같은 구조를 Lua로 구현해봤습니다.
> 쿠키가 없으면 라운드로빈, 있으면 고정입니다. 그런데 **기기를 바꾸면 다른 복제본으로 붙어서**
> '방금 산 코인이 안 보인다'가 재발하더군요. 실제로는 어떻게 다루시나요?"

관측 → 구현 → 한계 발견 → 질문. **이 순서가 되면 지적이 아니라 대화가 된다.**
