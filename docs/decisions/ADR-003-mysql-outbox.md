# ADR-003 · 전송 큐를 MySQL 아웃박스 테이블로

**상태**: 확정 (2026-09-01)

## 배경

전환이 발생하면 여러 매체(GA4, Meta, …)로 전송해야 한다. 전송은 외부 HTTP 호출이라 느리고 실패할 수 있으므로 **비동기 큐**가 필요하다.

## 결정

**MySQL 테이블(`dispatch_outbox`)을 큐로 쓴다.** Redis·SQS·RabbitMQ를 도입하지 않는다.

```sql
BEGIN;
  INSERT INTO conversions (...);                   -- dedup_key UNIQUE
  INSERT INTO dispatch_outbox (conversion_id, channel, ...) VALUES (...), (...);
COMMIT;
```

## 근거

**전환 데이터는 유실되면 안 되는 데이터다.** 별도 브로커를 두면 "DB에는 커밋됐는데 큐에는 안 들어갔다" 또는 그 반대의 정합성 구멍이 생긴다. 이걸 막으려면 2PC나 CDC가 필요한데, 이 규모에서는 배보다 배꼽이 크다.

**같은 트랜잭션 안에서 커밋되는 아웃박스 테이블이 이 규모에서 더 안전하다.** 전환과 전송 지시가 원자적으로 함께 기록되거나 함께 롤백된다.

처리량도 문제가 되지 않는다. 전환 이벤트는 페이지뷰가 아니라 **가입·결제** 단위라 초당 수천 건이 나올 성격이 아니다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **Redis (List/Stream)** | DB 트랜잭션과 큐 사이에 정합성 구멍. 영속성 설정을 강화하면 결국 DB와 같아짐 |
| **AWS SQS** | 위와 동일 + 네트워크 의존이 하나 더 늘고, 로컬 재현이 어려워짐 |
| DB 트리거로 큐 적재 | 로직이 DB에 숨는다. 디버깅·테스트가 어려움 |
| CDC (binlog → 큐) | 이 규모에 과함. 운영 부담이 애플리케이션보다 큼 |

## 결과

- **감수**: 폴링 방식이라 지연이 폴링 주기만큼 생긴다(기본 1초). 푸시 방식보다 느리다
- **감수**: 큐가 커지면 테이블이 비대해진다 → 전송 완료 후 90일 파기 배치로 대응
- **얻음**: `docker compose up` 한 줄로 전체가 뜬다. 컨테이너가 하나 줄었다
- **전환점**: 처리량이 늘거나 채널이 수십 개가 되면 그때 브로커를 분리한다. **지금 하지 않을 뿐 못 하는 게 아니다**
