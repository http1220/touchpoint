# ADR-020 · PG 를 직접 붙인다 — 하나로 모으는 자리는 웹훅 엔진이 아니라 상태 전이

**상태**: 확정 (2026-09-19) · **부분 이행** — 이니시스(국내 카드)만 붙였다. 페이팔(해외)은 보류.
[ADR-016](ADR-016-payment-and-notification.md) 의 결제 절을 이행한다.
리스크 목록 · 선택지 · 출처 전문은 [plan-multi-pg.md](../plan-multi-pg.md), 막힌 것은 [worklog 09-19](../worklog.md).

## 배경

가정 시나리오([plan 0장](../plan-multi-pg.md)): 잠김 · 중간 플랫폼 장애 · 세금과 정산 · 수수료 때문에
통합 PG 솔루션 대신 **코인 구매용 PG 를 직접 붙인다.** 국내는 이니시스, 해외는 페이팔.
과제로 적힌 것은 "PG별 API 연동 · 통합 어드민 · 에러 처리 · **PG별 웹훅 파싱 엔진** · 통화/수단 분기" 다.

ADR-016 은 `PgAGateway`·`PgBGateway` 자리를 비워 두고 *"두 번째를 붙일 때 무엇이 깨지는지를 기록"* 하라고 적었다.
그 전까지 결제는 스텁 하나였다 — `cli/pg` 가 서명한 웹훅이 `/webhooks/pg` 로 들어오는 경로.

## 결정

1. **하나로 모으는 자리는 `Payment_model::applyEvent()` 다.** 동기 결과(이니시스 승인)와 비동기 웹훅(스텁, 이후 페이팔)이
   모두 같은 조건부 UPDATE 전이로 들어간다. PG 마다 웹훅 엔진을 만들지 않는다
2. PG 마다 다른 것은 `src/Payment/Gateway/` 의 어댑터(`GatewayInterface`)에 가둔다 — 서명 · 승인 · 망취소 · 환불.
   결과는 `GatewayResult` 한 타입이다: `captured` · `pending` · `failed` · **`rejected`** · **`unknown`** · `refunded`
3. PG 거래 번호는 `payment_pg_refs`(`UNIQUE(pg, ref_type, ref_value)`)에 두고, **전이가 일어날 때만** 붙인다
4. **브라우저가 가져온 값은 믿지 않는다.** 승인·망취소 URL 은 모드와 센터 코드별 호스트에 https · 443 까지 완전 일치해야 한다.
   통과하지 못하면 HTTP 를 보내지 않고 **장부도 바꾸지 않는다**(`rejected`)
5. **결과를 모르면 그 요청이 망취소한다** — 승인 타임아웃(10초), 승인 뒤 DB 실패, 동시 복귀에서 진 쪽.
   망취소 URL 이 허용 목록 밖이라 되돌릴 수 없는 승인은 **요청하지 않는다**
6. 저장은 허용 목록 + 원문 sha256(`PayloadRedactor`). 카드번호와 구매자 정보는 5년 보존 범위에 들어오지 않는다
7. 어드민은 **CLI 만** — `cli/pg list · refund`, 그리고 `cli/verify payments` 의 오래된 결제 보고
8. 세무는 범위 밖이다 — `TaxPolicy` 인터페이스와 통과 구현(`PassThroughTaxPolicy`)만 두고 **아직 어디서도 부르지 않는다**

## 근거

### ① 이니시스 카드 결제에는 웹훅이 없다

결과는 브라우저가 우리 `returnUrl` 로 POST 하고, 우리가 그 요청에 실려 온 `authUrl` 로 승인을 요청한다(웹표준 매뉴얼 STEP2~4, [plan B3](../plan-multi-pg.md)).
과제의 "PG별 웹훅 파싱 엔진" 이라는 틀이 국내 PG 에서는 성립하지 않는다.

반면 **중복·역전 방어는 이미 전이에서 측정했다**([failure-scenarios D-3](../failure-scenarios.md)). 모으는 자리를 전이로 두면
새 PG 가 그 방어를 다시 만들지 않는다. 통합 테스트 8단계: 동시 복귀 8건(저마다 다른 tid) → captured 전이 1 · 붙은 거래 번호 1.

### ② 교차 사이트 복귀가 기존 전제 셋을 깬다

| 전제 | 깨진 모양 | 대응 |
|---|---|---|
| CSRF 보호는 모든 POST 에 | PG 에서 오는 POST 가 403 ([C2](../plan-multi-pg.md)) | `pay/inicis/*` 를 제외하고, 경로마다 CSRF 대신 무엇이 막는지 설정 주석에 적었다 — 시작은 `SameSite=Lax` 입장권 쿠키, 복귀는 호스트 검사와 금액 대조 |
| 결제는 쿠키로 사람을 안다 | `SameSite=Lax` 세션·방문 쿠키가 교차 사이트 POST 에 **실리지 않는다** (C3) | 주문번호로 결제를 찾는다. `Visitor` 를 부르지 않는다 — 부르면 복귀 주소를 랜딩으로 가진 유령 방문이 생겨 어트리뷰션 분모가 오염된다 |
| 외부 호출 주소는 우리가 정한다 | 승인·망취소 주소가 **브라우저 입력**이다 (C1) | 결정 4. 호스트 검사를 `endsWith` 로 바꾸는 변이에서 테스트 3건이 실패하는 것을 확인했다 |

### ③ 거절을 `failed` 로 적으면 위조 요청 하나로 남의 결제를 막는다

처음 설계는 승인 전 거절(위조 authUrl · 다른 mid · 인증 실패 코드)도 `failed` 로 적었다. 전부 브라우저가 가져온 값이다.
결제 번호를 아는 사람이 위조 POST 하나로 정상 결제를 `failed` 로 만들면, 진짜 복귀가 왔을 때 전이가 막는다.
그래서 **PG 가 거절한 것**(`failed`, 장부 반영)과 **묻기 전에 우리가 거절한 것**(`rejected`, 장부 불변)을 나눴다 ([C9](../plan-multi-pg.md)).

### ④ 스키마가 코드보다 좁았다 — 배포 전에 찾았다

복귀 승인을 `payment_events.source = 'return'` 으로 적게 짰는데 ENUM 은 `api`·`webhook`·`admin` 뿐이었다.
strict 모드에서 INSERT 오류 → 롤백 → `db-error` → **모든 승인이 망취소**됐을 것이다.
단위 테스트 502개는 DB 를 타지 않아 전부 통과한 상태였다. 스키마 정의를 대조하다 찾았고, 마이그레이션 `20260919000200` 과 통합 테스트 8단계를 더했다 ([B12](../plan-multi-pg.md)).

## ADR-016 의 가정 중 성립하지 않은 것

| ADR-016 | 실제 |
|---|---|
| "두 번째 PG 에서 인터페이스가 검증된다" | **아직 검증되지 않았다.** `GatewayInterface` 의 구현체는 `InicisGateway` **하나**다. 스텁은 어댑터가 아니라 `cli/pg` 가 서명하는 웹훅이다. 이번에 두 경로(웹훅 · 동기 복귀)로 검증된 것은 인터페이스가 아니라 **상태 전이**다. 페이팔을 붙이기 전에는 인터페이스가 옳은지 모른다 |
| "PG 는 테스트 환경이라 실제 정산·환불이 일어나지 않는다" | **틀렸다.** 이니시스 테스트 상점은 실제 카드로 승인하고 자정 전에 자동 취소한다. 그 취소를 **우리에게 알리지 않는다** ([D1](../plan-multi-pg.md)) — 우리 장부에는 `captured` · 코인 · GA4 매출이 남는다 |
| "상태값 이름 · 웹훅 페이로드 · 에러 코드가 PG 마다 다르다" | 차이가 더 크다 — **결과가 오는 경로 자체**가 다르다(동기 복귀 대 웹훅). 성공 코드도 한 PG 안에서 다르다(승인 `0000`, 환불 `00`) |

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 통합 PG(결제 오케스트레이션) | 시나리오의 전제다. 그리고 ADR-016 과 같은 이유 — 추상화가 이미 돼 있으면 "두 번째에서 깨지는 것" 을 겪을 수 없다. 단, **세금 사유는 통합 PG 가 판매 대행(MoR)형이면 반대로 뒤집힌다** — 직접 붙이면 우리가 판매자가 된다 ([plan 1장 A](../plan-multi-pg.md)) |
| PG 마다 웹훅 엔진 | 이니시스에는 웹훅이 없다. 중복·역전 방어를 PG 마다 다시 만들게 된다 |
| 승인을 아웃박스로 미룬다 | 사용자가 복귀 페이지에서 기다리는 동안 결과가 있어야 코인을 줄 수 있다. 웹 요청 안의 외부 HTTP([B11](../plan-multi-pg.md))를 받아들이고, 타임아웃 → 결과 불명 → 망취소로 닫는다 |
| 웹 어드민 · 대시보드 | 인증이 없다. 공개 페이지의 환불 버튼은 누구나 누를 수 있는 버튼이다 |
| 응답 원문 전체 저장 | 카드·구매자 정보가 5년 보존 범위에 들어온다([C5](../plan-multi-pg.md)). 허용 목록 밖 필드는 분쟁이 생겨도 복원할 수 없다 — 그것을 감수한다 |
| 실카드로 운영 검증 | 테스트 상점도 실제로 출금한다. **하지 않기로 했다**(사용자 결정). 대신 돈이 빠지지 않는 확인 둘을 했다 |

## 결과

**운영에서 확인한 것** (실카드 없이 — [plan 6장 「운영 확인 결과」](../plan-multi-pg.md))

- 우리 서명으로 스테이징 결제창이 열린다("코인 30개 · 3,300원"). 닫으면 결과 화면 — "승인을 요청하지 않았고, 청구되지 않았습니다"
- 위조 복귀(공격자 승인 URL) → 303, 승인 요청 0회, 결제는 `created` 그대로
- INIAPI 키 유효 — 없는 거래로 환불하면 `01 해당거래 없음`, 대조군(틀린 키)은 `ERR205 hashData 불일치`
- 카드 없는 한 바퀴 — 서명한 확정 웹훅을 같은 바이트로 두 번 → 전이 1 · 무시 1 · 코인 지급 1 · GA4·Meta 전송

**확인하지 못한 것**: 승인 요청(STEP3)의 서명 · 망취소 · 환불 **성공**. 가짜 `HttpClient` 로 쓴 단위 테스트로만 확인했다.

**받아들인 것**

- **멀티는 이중화가 아니라 지역 분할이다.** 지역마다 PG 가 하나라 그 PG 가 멈추면 그 지역은 결제할 수 없다
- 시연 결제가 운영 GA4·Meta 에 실거래와 구분 없이 간다([D2](../plan-multi-pg.md))
- 결제 화면을 공개하고 입장권 버튼을 뒀다 — 누구나 실승인을 일으킬 수 있다([C4 를 뒤집은 것](../plan-multi-pg.md))
- 모바일에서는 카드 결제창 대신 안내를 보인다. 이니시스 모바일은 별도 규격이라 붙이지 않았다([B10 을 뒤집은 것](../plan-multi-pg.md))
- PG 조회 API · 정산 파일 대사는 하지 않는다. 오래된 `created`·`pending` 은 `cli/verify payments` 가 **보고만** 하고 사람이 본다

**남은 것** — 페이팔을 붙일 때 검증한다

- 인터페이스가 두 번째 구현체에서 버티는가
- USD 가격표([B1](../plan-multi-pg.md)) · PG 소수 자릿수가 ISO 와 다른 것(B2) · 인증서 기반 서명의 자체 검증(B6) · 재전송 때 서명을 새로 만드는가(B8)
- 동기 capture 뒤에 오는 `COMPLETED` 웹훅 — 실제 PG 에서 저절로 생기는 중복 수신으로 D-3 을 다시 관측한다

## 되돌리는 조건

- 페이팔을 붙이다 **`GatewayInterface` 를 바꿔야 하면** 그 변경을 이 문서에 적는다. 그것이 ADR-016 이 기록하라고 한 바로 그 사건이다
- 결제 수단이 카드 밖으로 넓어지면(가상계좌 · 휴대폰) 서버 간 통지가 생긴다. 그때 "웹훅 엔진이 필요 없다" 는 판단을 다시 본다 — 그래도 **들어가는 자리는 전이 하나**로 둔다
