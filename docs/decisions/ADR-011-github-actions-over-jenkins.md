# ADR-011 · CI는 GitHub Actions (조직 표준은 Jenkins임을 인지)

**상태**: 확정 (2026-09-01) — 리서치로 **근거가 뒤집힌** 항목

## 배경

초안은 이렇게 적었다.

> "Jenkins 조직이라 **CI 공백**이 눈에 띔 → GitHub Actions"

즉 "이 회사는 CI가 약할 테니 내가 CI를 보여주면 돋보인다"는 논리였다.

## 문제

**전제가 틀렸다.** 조직의 CI/CD 구성을 확인한 결과, 공백이기는커녕 상당히 갖춰져 있다.

| 관측 | 의미 |
|---|---|
| 배포 잡이 **자동·수동 쌍**으로, 백엔드·프론트엔드·별도 언어 계통 **각각** 존재 | 자동화가 못 덮는 경로(승인·핫픽스)가 상시 있다 |
| 개발/실험 환경 전용 배포 잡이 별도 | **환경 분리(dev/stage)** |
| 컨테이너 레지스트리·서버리스 배포 잡 존재 | 클라우드 네이티브 워크로드 병행 |
| **테스트 자동화 잡 + 품질 지표 잡**이 별도 | 품질을 숫자로 관리 |

→ [조사 요약](../research-method.md)

**Jenkins가 있는 건 공백이 아니라 조직 표준이다.** 따라서 "CI 공백을 메운다"는 명분은 쓸 수 없고, GitHub Actions를 쓰는 이유를 **따로 대야 한다.**

## 결정

**GitHub Actions를 쓴다.** 단, 명분을 바꾼다.

| 이유 | 설명 |
|---|---|
| 저장소가 공개형 포트폴리오다 | 채용담당자가 클릭 한 번으로 **CI 통과 배지와 실행 로그**를 본다. Jenkins는 서버에 접속해야 보인다 |
| Jenkins는 서버 운영이 필요하다 | t3.micro에 Jenkins를 올리면 그것만으로 RAM이 끝난다 |
| 검증 범위가 같다 | lint + test + 이미지 빌드. 도구가 달라도 검증하는 것은 동일 |

**그리고 이 문서에서 조직 표준이 Jenkins임을 명시한다.** 모르고 안 쓴 것과 알고 안 쓴 것은 다르다.

## 파이프라인 범위

| 단계 | 내용 |
|---|---|
| lint | `php-cs-fixer --dry-run`, `phpstan` |
| test | PHPUnit (CI4 테스트) |
| build | `docker build` 성공 여부까지만 |
| **scan** | Trivy로 이미지 CVE 스캔 (1단계) |

배포는 CI에서 하지 않는다. 서버에서 `git pull && docker compose up -d --build`.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| Jenkins를 EC2에 구축 | t3.micro RAM 1GB. Jenkins 하나로 끝난다 |
| CI 없음 | 테스트가 도는지 보여줄 방법이 없다 |
| GitLab CI | 저장소가 GitHub에 있다 |
| Actions에서 SSH 배포까지 | 배포 키를 저장소 시크릿에 넣어야 한다. 포트폴리오 공개 저장소에서 위험 대비 이득이 적음 |

## 결과

- **면접 대비**: "Jenkins를 안 써봤나?"에 대한 답이 준비된다 — "조직 표준이 Jenkins인 건 잡 구조를 보고 알았습니다. 공개 저장소라 결과가 바로 보이는 Actions를 택했고, 검증 범위는 같습니다"
- **감수**: 실제 조직 도구와 다르다. **ADR이 그 간극을 메운다**
- **부가 발견**: `auto`/`manual` 잡이 쌍으로 존재한다 = 자동 배포로 못 덮는 상황(승인·핫픽스)이 있다는 뜻이다. 면접에서 물어볼 만한 지점
