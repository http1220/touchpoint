# ADR-008 · 결제는 스텁 PG, 상태 머신만 진짜로

**상태**: 확정 (2026-09-07)

## 배경

전환의 실체는 결제다. 실제 PG(토스페이먼츠 등)를 붙이면 진짜처럼 보인다.

## 관측

플랫폼 A 개인정보처리방침의 결제 위탁사가 **약 30개사**다.

> 다우기술, 다우페이, LG U+, KG모빌리언스, KG올앳, 세틀뱅크, 페이레터, 다날, SK플래닛, imPAY, 페이큐브, 카카오페이, 비바리퍼블리카(토스), NH페이코, 롯데멤버스, SafeCharge, T-money, 컬쳐랜드, 원스토어·Google·Apple, 카드사 9곳 …

→ [조사 요약](../research-method.md) 6-3

**PG를 하나 붙이는 건 이 문제의 축소판도 아니다.** 진짜 문제는 "30개를 어떻게 갈아끼우느냐"이고, 그 답(어댑터 패턴)은 이미 [ADR-005](ADR-005-channel-adapter.md)에서 매체 전송으로 보여준다. 결제로 한 번 더 보여주는 건 **중복**이다.

## 결정

**PG는 스텁으로 만들고, 상태 머신·멱등성·감사 추적만 진짜로 구현한다.**

스텁은 시나리오를 주입할 수 있게 만든다.

| 시나리오 | 검증 대상 |
|---|---|
| 정상 승인 | `created → pending → authorized → captured` |
| 승인 실패 | `failed` 전이, 전환 **미발화** |
| 응답 지연 후 클라이언트 재시도 | `idempotency_key`로 이중결제 차단 |
| **웹훅 중복 수신** | 멱등 처리 — 같은 이벤트 2회에도 상태 1회만 전이 |
| **웹훅 순서 역전** | 늦게 도착한 과거 상태 **무시** |
| 부분 환불 | `partially_refunded`, 코인 lot 회수 |

## 근거

**PCI DSS v4.0.1** 관점에서도 이게 맞다. 카드 정보를 서버가 받지 않고 PG에 전면 위임하는 것이 정석(SAQ-A)이고, 스텁은 그 구조를 그대로 흉내낸다. 실제 PG를 붙여도 우리 서버는 카드번호를 보지 않는다.

**전환 이벤트는 `captured`에서만 발화한다.** `created`에 보내면 실패 건까지 매체에 전환으로 집계된다. 이게 광고 연동과 결제 도메인이 만나는 지점이고, 이 프로젝트가 실제로 증명하려는 것이다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 실제 PG(토스) 연동 | 사업자 등록·계약 필요. 13일 일정에 리드타임이 안 맞음 |
| PG 테스트 모드 연동 | 리드타임은 줄지만 **얻는 게 상태 머신 검증뿐**이고, 그건 스텁으로도 된다 |
| 결제 전체를 생략하고 가입 전환만 | 결제가 없으면 `value_minor`·`currency`·코인 원장이 전부 무의미해진다. **가장 값진 설계 근거를 버리는 셈** |
| 다중 PG 어댑터 구현 | 어댑터 패턴은 [ADR-005](ADR-005-channel-adapter.md)에서 이미 보여줌. 중복 |

## 결과

- **README에 명시**: "PG는 스텁입니다. 검증한 것은 상태 머신·멱등성·감사 추적이며, 카드 데이터는 설계상 서버에 도달하지 않습니다"
- **얻음**: 실제 PG로는 재현하기 어려운 **웹훅 중복·순서 역전**을 마음대로 주입할 수 있다. 스텁이 오히려 검증에 유리하다
- **정직성**: 흉내를 실물로 포장하지 않는다. 이 문서가 그 증거다
