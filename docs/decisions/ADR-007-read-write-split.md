# ADR-007 · 읽기/쓰기 커넥션 분리와 복제 지연 재현

**상태**: 확정 (2026-09-07) — 리서치 결과로 **추가된 항목**

## 배경

초기 설계에는 없던 항목이다. 플랫폼 A 응답 헤더를 실측하다 이걸 발견했다.

```
Set-Cookie: …slave=sdb3; ... domain=.example.com
```

쿠키 이름이 **`slave`**, 값이 **`sdb3`**. **MySQL 읽기 복제본 중 3번에 이 세션을 고정(pinning)** 하는 구조다.

→ [조사 요약](../research-method.md) 3-2

## 왜 그렇게 하는가

읽기를 여러 복제본에 분산하면 **복제 지연(replication lag)** 때문에 *"방금 쓴 데이터를 못 읽는"* read-after-write 이상이 발생한다. 사용자를 한 복제본에 고정하면 최소한 **그 사용자 관점에서는 일관성**이 유지된다.

> **이 한 줄이 공고의 `MySQL` 태그가 실제로 뭘 의미하는지 말해준다.** 단일 DB에 쿼리 짜는 게 아니라 read/write 분리와 복제 지연을 다루는 환경이다.

## 결정 — 2026-09-08 개정: 흉내에서 실물로

**초판은 "복제본을 실제로 띄우지 않고 지연을 주입하는 시뮬레이션"이었다.** 근거는 t3.micro RAM 1GB였다.
[ADR-014](ADR-014-stack-alignment.md) 정렬 원칙에 따라 **실물 복제로 바꾼다.** 비용 편의를 이유로 목적을 포기하고 있었다.

| | 초판 | 개정 |
|---|---|---|
| 복제본 | 없음. 지연 주입 시뮬레이션 | **MySQL 복제본 실물** (GTID 기반) |
| 배정 | 앱에서 커넥션 그룹만 분리 | **OpenResty Lua가 쿠키로 배정** — 대상 조직과 동일 |
| 지연 | 코드에서 흉내 | **`SOURCE_DELAY`로 실제 복제 지연** |
| 인스턴스 | t3.micro | **t3.small** (2주 약 $15) |

### 구성

| 읽기 대상 | 실체 | 지연 |
|---|---|---|
| `rdb1` | 프라이머리를 읽기로 사용 | **0** |
| `rdb2` | 실제 복제본 | 실제 지연 + `SOURCE_DELAY` |

**같은 사용자가 어느 대상에 배정되느냐에 따라 보는 데이터의 신선도가 달라진다.** 이게 관측된 문제 그대로다.

### 배정 방식 — Lua

```
쿠키 없음 → 라운드로빈 배정 + Set-Cookie
쿠키 있음 → 그 대상에 고정 (재발급 없음)
```

관측된 동작과 동일하다. 구현은 [`docker/openresty/lua/replica.lua`](../../docker/openresty/lua/replica.lua).

### 앱에서의 커넥션 선택

Lua가 고른 대상은 `AB_READ_TARGET` FastCGI 파라미터로 전달된다. 앱은 그걸 보고 읽기 커넥션을 고른다.

| 경로 | 커넥션 | 이유 |
|---|---|---|
| `/collect` · `/conversion` · `/signup` · `/purchase` · 워커 | **쓰기(프라이머리)** | 쓰기 + 쓰기 직후 읽기 |
| 조회 전반 (내 코인, 열람 이력, 지표) | **읽기(배정된 대상)** | 여기서 지연이 드러난다 |

## 근거

이 결정의 가치는 두 겹이다.

**① 코드에서 "어느 쿼리가 어느 커넥션을 타는가"를 명시적으로 구분한다.** 그 구분이 없으면 복제본을 붙이는 순간 어디가 깨질지 알 수 없다.

**② 그리고 배정 자체를 엣지에서 한다.** 대상 조직이 그렇게 하고 있고([research 09](../research-method.md)), 이건 앱이 아니라 인프라 계층의 결정이다. Lua로 구현하면 **광고 연동 포지션과 인프라 포지션 양쪽에 동시에 걸린다.**

실물 복제이므로 **"결제 직후 코인이 안 보인다"** 가 흉내가 아니라 실제로 재현된다 → [failure-scenarios](../failure-scenarios.md)

### 그리고 한계가 금방 드러난다

쿠키 고정은 **같은 브라우저 안에서만** 유효하다. 기기를 바꾸거나 쿠키가 지워지면 다른 대상에 배정되어 문제가 재발한다.

> **그 한계를 발견하는 것까지가 경험이다.** 대상 조직도 같은 한계를 안고 있을 것이므로, 면접에서 물어볼 거리가 된다.

## 결과

- **비용**: 복제본 컨테이너 1개 + Lua 배정. 인스턴스 상향 포함 약 +1일, 2주 $15
- **얻음**: 면접 카드 — "쿠키에 `slave=sdb3`가 있는 걸 봤는데, 복제 지연으로 인한 read-after-write는 어떻게 다루시나요?"
- **한계 명시**: 복제본은 1대다(대상 조직은 5대 이상). 대수는 줄었지만 **실물 복제**이며, 흉내가 아니라는 점을 README에 밝힌다
