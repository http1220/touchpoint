# ADR-007 · 읽기/쓰기 커넥션 분리와 복제 지연 재현

**상태**: 확정 (2026-09-07) — 리서치 결과로 **추가된 항목**

## 배경

초기 설계에는 없던 항목이다. 플랫폼 A 응답 헤더를 실측하다 이걸 발견했다.

```
Set-Cookie: …slave=sdb3; ... domain=.example.com
```

쿠키 이름이 **`slave`**, 값이 **`sdb3`**. **MySQL 읽기 복제본 중 3번에 이 세션을 고정(pinning)** 하는 구조다.

→ [조사 요약](../research-method.md) 3-2

## 왜 그렇게 하는가

읽기를 여러 복제본에 분산하면 **복제 지연(replication lag)** 때문에 *"방금 쓴 데이터를 못 읽는"* read-after-write 이상이 발생한다. 사용자를 한 복제본에 고정하면 최소한 **그 사용자 관점에서는 일관성**이 유지된다.

> **이 한 줄이 공고의 `MySQL` 태그가 실제로 뭘 의미하는지 말해준다.** 단일 DB에 쿼리 짜는 게 아니라 read/write 분리와 복제 지연을 다루는 환경이다.

## 결정

복제본을 실제로 띄우지는 않되 **커넥션 그룹을 분리**하고, **지연을 인위적으로 주입**할 수 있게 만든다.

| 그룹 | 경로 | 용도 |
|---|---|---|
| `write` | `/collect`, `/conversion`, `/signup`, `/purchase`, 워커 | 쓰기 + 쓰기 직후 읽기 |
| `read` | `/metrics` 지표 화면 | 읽기 전용 |

```php
// 설정으로 지연 주입: read 커넥션에 지정 ms만큼 지연된 스냅샷을 흉내
'replicaLagMs' => (int) env('REPLICA_LAG_MS', 0),
```

## 근거

**단일 인스턴스에서 복제본 2대를 띄우는 것은 t3.micro에서 불가능하다.** 그러나 이 결정의 가치는 복제본 자체가 아니라 **"어느 쿼리가 어느 커넥션을 타야 하는가"를 코드에서 명시적으로 구분하는 것**이다. 그 구분이 되어 있으면 복제본을 붙이는 건 설정 문제가 된다.

지연 주입으로 **"방금 기록한 전환이 지표 화면에 안 보인다"** 를 재현한다. 이건 책으로 배울 수 없고 겪어야 아는 종류다 → [failure-scenarios](../failure-scenarios.md)

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| 아무것도 안 함 (단일 커넥션) | 관측한 실무 문제를 그냥 흘려보냄 |
| MySQL 복제본 컨테이너 실제 구성 | t3.micro RAM 1GB. MySQL 2대는 OOM |
| ProxySQL 등 미들웨어 도입 | 컨테이너 추가. 학습 목적 대비 비용이 큼 |
| 쿠키로 복제본 고정까지 구현 | 복제본이 1개뿐이라 고정할 대상이 없다. **개념만 문서화** |

## 결과

- **비용**: 커넥션 설정 2벌. 거의 0
- **얻음**: 면접 카드 — "쿠키에 `slave=sdb3`가 있는 걸 봤는데, 복제 지연으로 인한 read-after-write는 어떻게 다루시나요?"
- **한계 명시**: 실제 복제본이 아니라 **지연 주입 시뮬레이션**임을 README에 밝힌다. 흉내를 실물로 포장하지 않는다
