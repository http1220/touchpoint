# ADR-010 · Kubernetes·ECR을 쓰지 않는다

**상태**: 확정 (2026-09-07)

## 배경

조직의 CI 구성에 **컨테이너 레지스트리 배포**와 **서버리스 배포** 잡이 있다 → [조사 요약](../research-method.md). AWS 환경이고 컨테이너를 쓴다. 맞춰가고 싶은 유혹이 있다.

## 결정

**Docker + Compose까지만.** Kubernetes를 쓰지 않고, 이미지도 ECR이 아니라 서버에서 직접 빌드한다.

## 근거

**컨테이너가 4개다.** `caddy` / `app` / `worker` / `mysql`. 오케스트레이터가 관리할 것이 없다. 노드 1대에 파드 4개를 띄우려고 컨트롤 플레인을 세우는 건 **관리 대상이 늘어날 뿐 관리가 쉬워지지 않는다.**

ECR도 마찬가지다. 이미지를 push/pull할 노드가 1대뿐이면 레지스트리를 경유할 이유가 없다. `git pull && docker compose up -d --build`가 더 짧고 실패 지점이 적다.

**관측으로 뒷받침되는 부분**: 컨테이너 레지스트리·서버리스 배포 잡은 있는데 **Kubernetes 관련 잡이 없다.** 대상 조직도 ECS 또는 EC2+Docker로 보이며 K8s를 쓰지 않는 것으로 추정된다. 맞추려는 대상 자체가 K8s가 아니다.

> **다만 Docker 채택 근거는 이 관측으로 오히려 강해졌다.** "재현성"이 아니라 **"컨테이너가 조직 표준"** 이 더 나은 근거다.

## 기각한 대안

| 대안 | 기각 사유 |
|---|---|
| **Kubernetes (EKS)** | 컨테이너 4개에 컨트롤 플레인. 비용도 t3.micro 예산을 초과 |
| k3s / minikube | 학습 시연은 되지만 **이 프로젝트가 증명하려는 것과 무관** |
| ECR + ECS | 13일 중 인프라에 쓸 수 있는 시간은 2일. ECS 태스크 정의·서비스·ALB까지 가면 그것만으로 끝난다 |
| ECR만 사용 | 노드 1대에 레지스트리 경유는 순수 오버헤드 |

## 결과

- **감수**: 배포가 서버에서 빌드하는 방식이라 t3.micro에서 빌드 시간이 길다. **swap 2GB로 대응**
- **감수**: 롤백이 `git checkout <이전 커밋> && compose up`이다. 이미지 태그 롤백보다 거칠다
- **README 한계 명시**: Well-Architected 6기둥 중 **신뢰성을 의도적으로 포기**했음을 표로 제시한다 → [architecture](../architecture.md#8-의도적으로-하지-않은-것)
- **전환점**: 컨테이너가 10개를 넘거나 노드가 2대 이상이 되면 그때 오케스트레이터를 검토한다
